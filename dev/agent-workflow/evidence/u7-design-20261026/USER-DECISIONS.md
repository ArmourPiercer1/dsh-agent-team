# U7 user decisions (verbatim questions)

1. **R-U6P3-1 — governed bash positive:** Should Alpha.5 authorize a governed background/foreground bash call by (A) accepting team-root control arming the leader lane and reshaping the test expectation to include that leader-lane arming, (B) requiring a human to resolve via public `team.resolveControl` on the governed session (recommended; no permission/envelope change), or (C) adding a caller/lane-scoped bind-time grant/token to blueprint/control data (a new authority/envelope representation requiring a named center-interface PR)? **A** preserves current leader semantics but accepts broader test arming; **B** is smallest legal closure but requires a human-control live fixture; **C** gives precise lane isolation but changes approved authority semantics, adds protected center-interface work, migration and security review. Recommendation: **B**.

2. **R-U6P4-1 — governed background spawn:** Is governed background bash spawn an approved Alpha.5 capability for the REQUIRED `job_list/job_output/job_kill` obligations? **Yes**: implement the existing `attributeBackgroundJob` producer immediately after an authorized bash receipt is born, then prove owner fence/cancel/uncertain termination. **No**: keep all governed job trio calls fail-closed; this leaves REQUIRED G5 obligations with refusal-only behavior, which conflicts with the plan's prohibition on “功能必交项仅拒绝所有调用” and keeps G4/S5 blocked. Recommendation: **Yes**.

3. **R-G1F-2 — Domain family scope:** For `surface:domain_family`, should Alpha.5 (A) enumerate a finite set of Domain tools/scopes and deliver them as REQUIRED, (B) explicitly exclude Domain from Alpha.5's product/release claim with a documented boundary (recommended if no provider is approved), or (C) defer to Alpha.6 and keep G5 blocked? **A** increases obligations, provider/authority design and C3 cost; **B** narrows the release claim but lets unrelated Alpha.5 tools proceed; **C** preserves the current full-release blocker. Recommendation: **B** unless a concrete Domain provider and scope are approved.

4. **Bind-time token semantics (implicit in R-U6P3-1):** Is the absence of a lane-scoped bind-time token an intentional Alpha.4/5 semantic (then do not add one; use public human resolution), or is it an approved product gap that should be added to blueprint/control data? Choosing the latter changes permission/envelope/authority semantics and must be a named center-interface/security PR; choosing the former preserves `resolveControl`'s current leader/root authority and avoids a new token ledger. Recommendation: **intentional/current semantics**.
