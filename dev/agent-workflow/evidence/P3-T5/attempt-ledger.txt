## pwsh 5.1 CP936 encoding incident and recovery

Triggered during the D2 fix: two bulk-edit commands (pwsh `Get-Content -Raw` ->
`[System.IO.File]::WriteAllText`) round-tripped UTF-8 text through Windows
PowerShell 5.1's CP936 default decode, mojibake-ing all non-ASCII content
(Chinese comments, section signs, em dashes) in 14 files: 7 compatibility src
files (index.ts was skipped by an edit guard and only later touched by the
recovery itself) plus all 7 test files.

Recovery steps:
1. Backup of all affected files to `.t5-recover-backup/` (deleted after recovery).
2. Byte-level inversion: UTF-8 read -> GBK(936) encode -> repair the one known
   byte pattern E2 80 3F -> E2 80 94 (em dash) -> mark remaining
   `[E0-EF][80-BF]3F` sequences as EF BF BD (U+FFFD) -> UTF-8 decode.
3. Seven manual codepoint-level repairs for lost bytes. All replacement
   strings were built from `[char]0xXXXX` codepoints because non-ASCII
   literals in the pwsh 5.1 command line are themselves mangled: 6 isolated
   U+FFFD (U+8BB8 x4, U+52A8, U+5B9A) plus 1 double U+FFFD (-> U+00A7 in
   engine.ts).
4. index.ts restored verbatim from backup (never corrupted; the inversion
   itself had damaged that clean file).

Verification: grep over the entire packages/ tree for mojibake signatures
(GBK-mojibake byte pairs, incl. U+FFFD) -> 0 matches; codepoint dumps confirm
U+00A7 (section), U+2014 (em dash), U+672A U+77E5 (Chinese). All files re-ran
green afterwards (D9).

Lesson recorded for future tasks: never round-trip UTF-8 text through
Get-Content/Set-Content without explicit encodings (`[System.IO.File]::
ReadAllText/WriteAllText` with a no-BOM UTF-8 encoding), and never pass
non-ASCII literals through a pwsh 5.1 command line.
