### Reuse decisions (no duplication)
- Durable provisioning = P4-T4 `ProvisioningCoordinator` (journal prepare = ALLOCATED reservation ->
  adapter child create + `journal.recordChildSession` -> `ensureMemberRecord` (record carries child, inv 23)
  -> P4-T3 `createTeamMemberBinding` -> `journal.drive` ledger fact + COMMITTED). ONE coordinator instance
  per rootSessionId (team-scoped, cached in a Map).
- instanceId allocation INSIDE the journal protocol (task card): instanceId is derived from the caller's
  LOGICAL OPERATION token, not from the spec string (P5-T6 `deriveMemberIdentity` collides for same-template
  parallel creates). `instanceId = 'inst-' + deterministicToken(activationKey, 12)` where
  activationKey = [rootSessionId, source, requestToken].join('\u0000'). Same token -> same instanceId ->
  same operationId (`provisioningOperationId`) -> same idempotencyKey (`provisioningIdempotencyKey` with
  allocationToken = requestToken) -> convergent replay. Different token -> different id (inv 17: one
  template -> 0..N instances).
- The coordinator's `AgentFactoryAdapter` (the ONE external effect) is implemented by an ACTIVATION adapter:
  `childSessionFactory.createChildSession(...)` (injected port; real DSH seam later) then the UNCONDITIONAL
  `sessionDurability.ensureDurable(childSessionId)` barrier (P5-T6 invariant, never conditional, inv 46).
- The binder (P5-T1 `TeamAgentBinder.bindFreshMember`) runs POST-commit, NOT inside the adapter:
  `bindFreshMember` resolves session kind via the read handle and requires the team-member binding + member
  record to exist (they are created in coordinator stages 2-3 / commit). This matches P5-T6 precedent where
  the binder ran after all durable puts. The child session artifact itself is durable BEFORE the
  MemberInstance commit (barrier + recordChildSession precede ensureMemberRecord/commit).
- Post-commit effects (binder + projection) are idempotent, so the crash window "COMMITTED but binder not yet
  installed" converges on re-drive. Roll-forward, never rollback (Arch 18).

### Admit-once rule (crash-safe retry semantics)
- `activate(request)`: compute instanceId from the logical token; if a durable operation row ALREADY exists
  for it (any phase: PREPARED or COMMITTED) -> the operation is already ADMITTED: skip admission checks and
  re-drive the durable stages idempotently (roll-forward). Only when NO operation row exists do the 11
  read-only admission checks run, then the reservation (journal PREPARED) happens. A same-token replay after
  commit therefore returns the original member (replayed: true) and is never re-blocked by a changed
  environment. A same-token request with DIFFERENT content under the same operationId -> journal
  IDEMPOTENCY_CONFLICT -> ACTIVATION_IDEMPOTENCY_CONFLICT (loud).
- `recoverActivation(request)`: explicit recovery entry; identical to the re-drive path (no admission
  re-checks by construction).

### Binder admission decision (post-commit)
- Per P5-T1 contract: a `rejected` guard decision completes the overlay install but keeps the work gate
  closed; the activation SUCCEEDS and reports admission:{admitted:false, code}. A throwing guard ->
  ADMISSION_GUARD_ERROR (fail-closed, same reporting). The tools layer gates work on admitted===true.

### Failure matrix (fail-closed)
- Steps 1-11: ActivationError, ZERO durable writes (asserted in tests over a recording proxy).
- Step 12+ (after PREPARED): the PREPARED row remains; recovery re-drive converges (journal idempotency +

- Journal IDEMPOTENCY_CONFLICT -> ACTIVATION_IDEMPOTENCY_CONFLICT; CHILD_SESSION_CONFLICT ->
