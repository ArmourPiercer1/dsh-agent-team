    feat(a4-pr7): 7.0 A1-14 authority-scope persistence + consumption recheck
    
    The prerequisite of Task 7, implemented rather than amended away: the
    approval case now carries the concrete authority POINT it was decided on,
    and `guardOperation` re-runs the ceiling for that point inside the
    per-team lock, immediately before the `control-allow-consumed` write.
    
    Persistence (control/types.ts, control/service.ts):
    - `ControlAuthorityScope {operationClass, matcher:{kind:exact|fingerprint,
      resource}}` on `ControlOperationScope`, `ApprovalCaseIdentity`, the
      request payload, the leg fields, the decision snapshot and the scope
      snapshot comparison. `subtree`/`any` are deliberately NOT matchable
      kinds for a durable point: a region matcher would turn a single-shot
      approval into a standing ceiling.
    - The identity law: an operation case whose identity carries no point is
      REFUSED at the write (`authority-scope-required`). A durable row that
      carries no point is corrupt, not merely unsampled: the case read files
      it as `identity-disagreement` and the guard refuses with
      `authority-scope-unbound`.
    - `parseScope` and `commitDecision` both project the point. Omitting it in
      either place drops the fact the recheck reads and answers
      `scope-mismatch` for the correct operation — both sites are pinned by
      the new test's A1 (a green run is only reachable if the point survives
      request row, decision snapshot and guard scope).
    
    The recheck (control/types.ts port, service.ts call site):
    - `ControlAuthorityRecheckPort` is a CLOSED VERDICT PORT
      (`still-sufficient | authority-risen | undetermined`). The control lane
      never names the ceiling evaluator, the ladder, or the document slot —
      `a3p3-governance-lane-hygiene` states that consumer set in full and the
      control lane is not in it, so the allow-list stays exactly as wide as it
      was.
    - Refusal reasons `authority-risen`, `authority-undetermined`,
      `authority-scope-unbound`; all three write NOTHING (zero consumption),
      and none of them is ever routed into `no-request`, which is the one
      verdict `packages/tools/src/guard.ts` proceeds on.
    - ABSENT PORT IS NOT "COVERED": with no port a v3 operation approval is
      unconsumable. Fail closed rather than default to yes.
    
    Composition (approval-routing.ts, permission-plane.ts, root.ts):
    - `recheckPersistedOperationAuthority` asks the PERSISTED question, with
      the persisted matcher kind, through the one evaluator. It is a separate
      function from PR4's `recheckOperationApproval` because that one takes the
      fresh ROUTING, whose scope question is `exact` by construction — a
      fingerprint-shaped point evaluated under an exact question reads as
      "no rule covers this", i.e. an authority rise reported as still-covered.
    - The plane composes the port (`createControlAuthorityRevalidation`) over
      the SAME operation-facts reader the ask routes with, and publishes it to
      the control service through a lazy ref in `root.ts` (the root's
      established pattern): two readers would be two answers, and here the two
      answers decide whether an approved operation executes.
    - `pre-execute-adapter.ts` supplies the point at the case identity AND at
      the guard, names the three new guard refusals with their own outcome, and
      its PR4 SCOPE DISCLOSURE (that half of A1-14 was UNENFORCED at the
      consumption write) is retired.
    
    Disclosed, not fixed here (the shell-class matcher question): for
    `bash`/`pwsh`, a document rule of shape
    `{operationClass:'bash', matcher:{kind:'fingerprint'}}` does not cover an
    `exact` target, so a narrowing declared at that shape is invisible to the
    ASK (PR4's design, which this commit does not change) and therefore to the
    recheck too. Widening the ask changes which rung the shell class must ask
    for — a cutover decision with its own routing evidence, not a persistence
    task. The durable field carries a matcher `kind` so the fix lands at one
    site later without a shape change.
