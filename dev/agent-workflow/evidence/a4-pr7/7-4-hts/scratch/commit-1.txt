A4-PR7 §7.4 (C-tools+harness 1/5): migrate the P5-T5 harness Blueprint source to v3

packages/runtime/root-binding/harness/blueprint-source.mjs is the bounded-run
harness's OWN boot document: root-binding/harness/plugin.mjs:431 feeds it to the
production parser (`parseBlueprint`) at row setup and derives the snapshot ref
(`blueprintId`/`revision`/`contentHash`) from that parse. The version line is
therefore read by the product, not by a test — the fence's `dirty` verdict is
correct and the disposition is migrate-by-hand, not delete-lie. After §7.3's flip
a v1 document is refused at that call, so leaving it would break the harness.

v3 requires BOTH authority documents and never defaults them
(domain/blueprint/src/validate.ts:1335-1336). Both are carried as `rules: []`,
which is the narrowest legal value and exactly what this harness always declared:
its v1 document carried neither carrier, and an absent carrier is a typed absence
meaning zero expansion authority — the same ceiling the reader derives from a
declared-empty one (`authority-envelope.ts`, "an absent hard document is
no-authority"). No P5-T5 scenario opens an expansion, so any rule written here
would be authority the harness never exercises. Nothing else in the document
moved: identity, personas, requirements, envelopes, policyStates and quotas are
byte-identical, and no rule was added to the fence or its scope.

No hand-copied hash to re-pin: run.mjs:344 carries no contentHash ON PURPOSE
("the snapshot ref is derived from the parsed blueprint document") and
plugin.mjs:439 refuses on mismatch. The derived identity is printed by the probe,
not asserted here: v1 `sha256:a22c7816f98bc462e29b62e35fdda898051cccdad0a90157485f96834c3a71b5`
→ v3 `sha256:a7f3203fba5ab13215054fdc5a9ace02318a934ca41d15f09aaf8625d6e838b5`.
