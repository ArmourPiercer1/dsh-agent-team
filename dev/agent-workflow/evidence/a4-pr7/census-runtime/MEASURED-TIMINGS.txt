upload, and a cold pnpm download of BOTH trees — and the local floor for the hosted job is
"8 minutes plus", with the pnpm downloads the least predictable part.

THE HOSTED FACTOR (the only measured one)
-----------------------------------------
`pr-gate`'s hosted 7-leg run (37794562230, evidence/a4-pr7/ci-gate/FINDINGS.md): 475.3 s on
`ubuntu-latest` against 222.4 s locally for the SAME legs — and the hosted one did strictly LESS
work, because its census refused instantly. A conservative per-leg factor is therefore 2–4x, and
the census is the part that scales with cores (each capture spawns real DSH hosts, and the published
baseline itself declares a load family). 4x the local floor is ~32 min; the job asks for 60 and
explains why in its own comment. NARROW IT from the first hosted run's per-step timings.

ALSO MEASURED, NOT TIMINGS
--------------------------
* GitHub answers `git fetch --depth 1 origin <sha>` for the pinned object (verified against
  github.com from this sandbox twice, and again inside the E2E): the pin cannot be silently
  replaced by a moved branch tip, and the drift control proves the assertion bites.
* `git ls-remote … stable-3-0.2.0-rc.2` == `TEST_USE_BASELINE_SHA` in tests/paths.mjs
  (639ed015397290b3745d163aafe02ffee4aa3f84), re-confirmed 2026-10-08 (UTC).
* The host's `package.json` version at that SHA is `0.2.0-rc.2` == `DSH_BASELINE_VERSION`, so the
  provision step's third assertion is satisfiable, not aspirational.
* A host `pnpm run build` leaves the pinned tree porcelain-clean (0 lines), both in the probe and in
  the E2E — which is what makes the post-build pin re-assertion safe to run.
* With `CI=true` — which this job sets, and which makes pnpm default to `--frozen-lockfile` — the
  pinned host's `pnpm install --ignore-scripts` exits 0 ("Already up to date"): the TEST_METHODS §2
  chain survives the CI default, so the job need not weaken the host install to make it work.
* Census shape seen twice, on two different hosts (shared pristine checkout; freshly fetched+built
