=== RED CONTROL F (unplanned, and the more credible for it) — an undisclosed load-sensitive leg refused the tip ===

This is not a planted control. It is the second  run of this gate, on the unmodified tip,
and the gate said NO where a count-based gate would have said yes.

What happened, in one line: capture 1 of 2 of the nine-root census saw the published 22 reds;
capture 2 saw 23. The extra identity is not in the population baseline and not in the one load
family the baseline discloses. The census leg therefore had no tolerance to apply, reported
NEW RED(S) 1 naming the identity, and the run ended DSH-CI-VERDICT fail.

--- the identity, and the two timings behind it ---
TEST packages/runtime/test/a3p3-governance-lane-hygiene.test.ts::the shared authority grammar stays a DOMAIN LEAF (A4-PR1, ADR A3-9/A2-3) the ceiling adapter and the PR2 evaluator each have ONE audited consumer set per name

  capture 1: passed in 4443 ms
  capture 2: FAILED — "Error: Test timed out in 5000ms." after 6938 ms (vitest default testTimeout, no override in vitest.config.*)

--- measured durations of that same leg, from the stored vitest JSON reports ---
  closure lane @9df5535f (a tree before this lane existed): 4589 ms  passed
  this lane, run 1 capture 1:                              4424 ms  passed
  this lane, run 1 capture 2:                              4094 ms  passed
  this lane, run 2 capture 1:                              4444 ms  passed
  this lane, run 2 capture 2:                              6938 ms  FAILED (timeout)

So the leg runs at 80-92% of its own timeout under a full-suite load, and one capture in four
of this lane's runs crossed it. Its cost is a full readdirSync walk over every shipped package
(packages/runtime/test/a3p3-governance-lane-hygiene.test.ts:153, :261, :351, :550), which is why
load moves it. Whether this lane's own ~1400 added lines contributed is NOT established: the
walk is over packages/** and this lane adds no file under packages/.

--- what the gate did, and did not, do about it ---
  DID  : graded the union of the two captures (a red seen once is a red), named the identity,
         and exited 1 — see RED-F-full-run-refused-the-tip.txt, DSH-CI-VERDICT fail pass=6 fail=1.
  DID NOT: add the file to the tolerance. The first draft of scripts/ci-pr-gate.mjs hardcoded
         one family name (p6t1-parallel.test.ts), which is an exemption list kept by the gate's
         author; parseLoadFamilies() now reads the disclosed families out of the baseline
         document instead, so the remedy is a disclosure by whoever owns that leg (or a raised
         timeout / narrowed walk), and the gate cannot be quietly taught to forgive this one.

Reproduce: node scripts/ci-pr-gate.mjs --full --census-captures 2
Observed rate of THIS leg going red under a full run: 1 of 4 captures, on one machine, n small.

3 failures in 7 default-clock observations — but the number matters less than the shape. The
passing runs cluster in 4.09–4.91 s and the failing ones in 6.63–6.96 s. There is nothing in
between: the leg is bimodal, and the 5000 ms budget sits INSIDE the gap between its two modes.
That is a stronger statement than "it is load-sensitive under a full-suite run", and a different
remedy: a budget has to clear the upper mode (~7 s) or the walk has to get cheaper, and any budget
in the 4.6–6.6 s range would be a coin flip wearing a confident number.

The 20000 ms rows are the same leg on the same tree, and one of them passed at 6775 ms — the upper
mode is normal, not pathological.

by `packages/testkit/test/rc2-sanitize-evidence.test.ts::…S13 file aliases…`: the census named it as
a new red, that capture's reporter had printed `✓ …S13… 4379ms` for the same leg, and the capture's
