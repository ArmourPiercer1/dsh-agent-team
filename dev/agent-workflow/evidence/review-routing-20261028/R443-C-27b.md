## C3 — Security reasoning  ✅

**(a) Can a hardlink planted AFTER open-but-before-write redirect this append? No — the comment's FD-pinning claim is correct.** Once `open(O_WRONLY|O_CREAT|O_APPEND|O_NOFOLLOW)` succeeds, the fd is bound to a specific inode (kernel `struct file` → inode pinning). Any later `link`/`unlink`/`rename` on any path name cannot change the inode the fd references, so the `write` via that fd lands on the opened inode, period. A post-open link at worst (i) makes the about-to-be-appended bytes *visible* under the alias name — but the alias points at the same inode that the ledger name already points at, and `link(2)` on the source requires local read/write access to the 0600 file in a 0700 dir, i.e. the attacker already has direct read access to the ledger: no new exposure class; (ii) makes `nlink > 1` visible to the *next* operation's guard. The guard's real job — closing the **pre-open** alias (the persistent, realistic threat: name aliased outside the root before the store appends) — is done by the fstat-on-fd check and is empirically proven by the tests (external file byte-unchanged, typed refusal, zero disk write). The only unpreventable residue (a link landing in the fstat→write microsecond window) is exactly the deferred sharing axis the comment names — not a redirect, so "closes the escape axis for this operation" (write-destination containment) stands.

**(b) Does the newly-throwing `ledgerBytes` break any caller?** Repo-wide grep (packages/tests/scripts, excl. dist/node_modules): the real call sites are (1) the store's own `writesBytes` closure (:877) — no in-repo consumer of `writesBytes()` exists beyond the C1 test's type declaration (`u7-agentstate-fs-store-c1.test.ts:51`); (2) the lane-face re-export (`index.mjs:32`) — no in-repo consumer found; (3) the audit test itself, which asserts the new contract (absent→0, empty→0, sized→N, EACCES→throws `AGENT_STATE_STORE_LEDGER_UNREADABLE`). `center-shadow-row.mjs:94`'s `ledgerBytesWritten` is an unrelated local marker field (verified in context). No caller depends on the old "any error → 0" behaviour; the tri-state (0 | N>0 | THROW) is now documented at the function. Matches the expected caller set (store.writesBytes + tests).
