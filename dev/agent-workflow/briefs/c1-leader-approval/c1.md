## 0. Problem (C1 = reachability/liveness, NOT authority)

When a member's permission ask created a durable `leader-approval` control
request, the LEADER had no discoverable, reachable path to find and resolve
it on a real host:

1. No notification: `requestControl` created the durable row but never
   informed the Leader session (the request was reachable only by
   inspecting the ledger storage — the model-facing surface had no
   discovery tool).
2. No discovery tool: the closed team tool surface (11 tools) had no
   read-only pending-list capability; a Leader that missed the moment
   could not enumerate open requests.
3. Synchronous-delegation trap: a Leader blocked in a sync `team_delegate`
   cannot process its own notification until the delegate returns, which
   requires a decision the blocked Leader would have made — a cross-session
   cycle only the human resolver channel breaks.

## 1. Scope (FROZEN — plan §11 forbidden fixes stand)

- NO auto-allow, NO second ControlService, NO messaging routing, NO
  lock-held delivery, NO C2 code, NO core changes.
- Resolver roles, decision authority, request scope, guard semantics, and
  the durable ledger vocabulary are UNCHANGED.

## 2. Implementation (committed in this branch)

### 2.1 `packages/tools` — the 12th tool

- `team_list_pending_control` (read-only, Leader-only before any read):
  lists UNRESOLVED `leader-approval` requests for the root (filter:
  pending = no decision row; kind = leader-approval), sorted by
  requestSequence, `limit` 1–100 (default 50) + `truncated` flag.
- New result discriminant `pending-control-listed` (closed-union
  convention) + error `TEAM_TOOL_PENDING_LIST_NOT_LEADER`.
- Tool catalog 11 → 12 everywhere (spec list, docs, six test pins:
  d1-member-base-tools, t12a-team-tools-registration, t4a-capability-
  wiring, tcm-d4-root-context, p6t6-bypass-scan, p8s5a-production-assembly;
  two comment refs: multi-mcp-wiring:216, root.ts:1901).

### 2.2 `packages/runtime/control` — notification port

- `ControlRequestNotificationPort` (`packages/runtime/control/leader-
  notification.ts`): a pure renderer — line 1
  `[team-control requestId=<id>]`, the request lines (requestId:/requester:
  /target:/optional tool:/summary: — summary bounded at 256 chars), and
  the guidance lines naming `team_resolve_control` (`allow`/`deny`) and
  `team_list_pending_control` (recovery/inspection).
- `requestControl` now runs inside the team lock and returns
  `{record, created}`; AFTER the lock releases, a fire-and-forget
  `notifyLeaderRequest` runs only when `created && kind ===
  LEADER_APPROVAL` (idempotent retries never re-notify; `onNotification-
  Failure` hook records the failure without touching the decision state).

### 2.3 `packages/runtime` — wiring (no MessagingCoordinator)

- `agent-bindings.mjs`: `deliverRootControlNotification({rootSessionId,
  requestId, text})` (validates non-empty; `await deliverRootInput`) — the
  notification lands as a model-visible input turn on the created team's
  Leader root.
- `root.ts` / `types.ts`: optional port + `createLeaderControlNotifier`
  conditional wiring.
- Upstream fact verified this round (test-use rc.2 checkout,
  `packages/core/session/src/repair.ts`): a crash-orphaned tool call is
  NOT redriven on resume — the session repair appends a synthetic
  "interrupted" tool result and closes the turn. (Constrains what
  "retry" can mean on a real host — see §4 S5.)

## 3. Documented deviations (justified in the final report)

1. **Result discriminant** `pending-control-listed` (not
   `"status":"executed"`): the closed-union result convention.
2. **Notification = fire-and-forget** (`void port.notifyLeaderRequest(...)`
   after `withTeamLock` releases): in the sync-delegation topology,
   AWAITING delivery inside the request path forms a cross-session cycle
   the Leader itself cannot break (plan §3.3/§3.4/§5).
