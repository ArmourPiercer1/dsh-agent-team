## 三、我认为必须修改的设计合同

### 1. 修正执行事实持久化的崩溃一致性定义

这是我认为 #765 中最值得在正式实施前补充的一点。

现有设计规定：

- S1：每次进入执行阶段的调用，最终都有可查询的执行事实或显式 `unknown`。
- S2：执行事实在模型看到结果之前已经持久化。

两项要求本身合理，但文档声称 S2 达标自动蕴含 S1，逻辑上并不成立。

考虑一种故障：

```
工具进入执行阶段
    ↓
实际产生文件副作用
    ↓
Host 发生 SIGKILL
    ↓
模型尚未收到 ToolResult
    ↓
持久化系统中没有对应 ExecutionId
```

由于模型没有收到结果，单独的 S2 返回前持久化要求可以没有被违反；但 S1 已经失败。

我建议将 S1 的实施合同改为：

任何可能产生副作用的工具执行，在进入真实执行之前，必须存在可恢复的持久执行意图。

恢复时，即使无法确认 Body 是否进入，也应保守地将相应调用结算为 `EXECUTION_UNCONFIRMED`，而不能让它从系统里消失，更不能自动重放。

具体设计需要明确 `ExecutionId` 分配、持久化确认、Grant 消费和实际 dispatch 之间的顺序。这不仅是测试问题，也决定 Journal 是否真正满足 S1。

S2 则应定义为 S1 加上 commit-before-model-visible-result 的附加保证，这样两者的包含关系才严格成立。

### 2. 让 FS 语义差异成为明确的架构决策，而非长期挂起的阻塞项

\#792 发现了两项真实差异：

拒绝错误码差异

旧路径使用 `FS_SANDBOX_DENIED`；原型使用 `FS_PERMISSION_DENIED`。rc.5 的原生 FS 工具会在处理前一种错误码时访问 sandbox policy，因此不能简单复用它。

错误表达形式差异

旧路径的部分拒绝是文本消息，新路径使用结构化 `FsError`。现有向量只比较拒绝类别与最终效果。

这些差异不一定意味着需要修复上游，更不意味着必须 Fork。

我建议在 #765 中明确：对外可观测的拒绝行为保持兼容是目标，但内部错误码并不要求逐字相等。

应先确定哪些调用方依赖旧错误码和文本，再决定使用上游 sandbox 协议、在受信边界转换错误，还是正式批准语义变化。只有完成这个决策和相应测试，才解除两项 retirement blocker。

对于读取能力，继续保留 #791 已实现的限制：快照式 Oracle 只能证明可观测的文件效果，不能证明未授权读取没有发生。如果未来希望宣布严格 read confinement，需要增加 Provider/OS 层的读取观测证据，而不是放宽当前验收规则。

原来的 G0–G5 总体分层可以保留，但不应该再把它当成单一串行开发队列。较合适的是按可运行的纵向功能推进，每完成一个阶段就获得独立可复核的成果。

阶段 A

基线更新

现在执行

阶段 B

并行开发

G1-S4 基线 + G1-S1 实际集成

一条任务线建立旧工具族可运行 golden baseline；另一条将 FS 原型挂入真实 rc.5 Agent/World，检验身份绑定、生命周期、实际效果与拒绝，并保留旧路径。两条不必相互阻塞开发，但退役前必须汇合验收。

阶段 C

接口与结算

G1-S2 Web + G1-S3 Journal + G1-S5 探测

Web/Search 路由透传可独立推进；Journal 完成 S1 的持久化和 kill -9 恢复负控；S2 的公开等待点探测可以提前并行，避免到最后才发现必须调整 Host 接缝。

阶段 D

正式迁移

G2–G4 → G5

统一 Leader/Officer/Member Binding 和真实执行边界，逐一处理 FS、Web、Subprocess、PTY、PTC 的效果与恢复。只有各工具族等价或语义变化已获批准，且真实负控满足后，才按族切换与退役旧实现。

这个顺序相较 #765 原方案有三个实质变化。

第一，G1-S4 应提前，而不是等到其他 G1 功能完成才建立旧路径基线。 不需要先收齐全部工具族才能继续写 FS 原型，但每个工具族的退役必须有对应基线。

第二，S2 的公开接缝研究应尽早进行。 它不阻塞 S1，也不应导致提前 Fork，但越早发现 Host 在最终结果路径上的限制，后续 Settlement 设计越不容易返工。

第三，G2–G4 需要按效果域分别验收。 特别是 Process、PTY、PTC 的真正 OS 约束，应采用与实际内核能力相匹配的正负控。此前 Linux ABI 差异已证明，不能简单地要求所有平台产生相同的允许/拒绝结果；能力不足时应在执行前明确拒绝。

## 三、发现的主要架构与实现风险

### 1. 高优先级：FS 的实际退役单位与验收覆盖不一致

这是目前最重要的发现。

我直接读取了 master 中的 `packages/tools/families/fs.mjs`。现有受管 FS Family 并不只是 `read/write/edit`，而是将以下四个工具作为一个不可拆分的 FamilyAssembly：

`read`、`write`、`edit`、`read_image`

它明确要求四个工具共同装配，不能因其中某一个缺失而自动回退到未受管的原生工具。

但 #793 的 FS 退役账本已经将：

- `OldBaseline = true`
- `NewPathVerified = true`
- `NegativeControlsPass = true`

这些结果主要来自 #792 的 10 个 FS golden vectors。它们没有完整覆盖 `read_image` 的附件存储、模型图像能力路由、拒绝与取消语义。#796 也明确承认没有完成 `read_image` 的相应验证。

结果是：只要将当前两项 FS 语义差异标记为已批准，现有四条件退役门禁在逻辑上就可能允许整个 FS Family 退役，而实际没有验证其四工具全集。

这是合同完备性问题，不是简单补几个测试就能解决的问题。

我的建议是：

1. 在 `RETIREMENT.md` 中明确 `fs` 的工具成员全集，以及它们共同依赖的受管服务。
2. `NewPathVerified` 必须覆盖这个全集，或将退役单位重新定义为经过证明可以独立切换的更小单元。
3. 对每个成员都记录新旧行为、异常、取消与必要的副作用证据。
4. 扩展机器门禁，拒绝覆盖不完整的退役记录。

在这一点修正前，我建议禁止启动 UTE-4 的任何实际删除操作，也不批准 FS Family 的生产切换。

### 2. 高优先级：UTE-2 的实际接口与已冻结合同不一致

[UTE-0 CONTRACT.md](https://github.com/ArmourPiercer1/dsh-agent-team/blob/master/docs/plans/memo/ute-g1-20261120/CONTRACT.md?utm_source=chatgpt.com) 定义的 `ExecutionSettlementWriter` 接口包含：

`record()`、`read()`、`listUnsettled()`、`projectControlResult()`

然而 #795 实际实现的 `ExecutionSettlementStore` 提供：

`recordAdmission()`、`enterRunning()`、`recordStop()`、`settle()`、`recoverUnsettled()`、`read()`、`list()`

这不是单纯的函数重命名。实现新增了很有价值的内部状态机，但没有兑现合同中明确要求的 `listUnsettled` 和旧 `ControlService.recordExecutionResult` 兼容投影。

我认为 #795 的设计可以保留，但应明确区分：

- SettlementStore：负责持久化、状态转移、冲突检测和恢复。
- ExecutionSettlementWriter Adapter：提供 UTE-0 约定的接口，连接现有 ControlService 与 DSH 执行事件。

另外，当前实现的 `recordAdmission` 可以作为持久执行意图，但还没有证据证明它一定在产生副作用之前完成，也没有证明其身份和审批引用由受信组件提供。

还有两项持久化边界需要写清：当前文件写入采用 `fsync` 加原子 `rename`，但没有对父目录执行 `fsync`；跨进程并发写入同一 ExecutionId 也没有明确的互斥机制。如果部署模型保证单进程唯一 Writer，可以不引入复杂的分布式存储，但必须把这个前提写成合同并验证。

裁决：#795 可以继续完善，但在 Writer Adapter、唯一 Writer 前提和 dispatch 崩溃窗口明确前，不允许接入正式工具执行链，也不能宣布 S1 达标。

### 3. 高优先级：UTE-1 的 Scope Disposal 不等于执行排空

我检查了 #796 的 `packages/tools/src/native-fs-binding.ts`。

目前 Scope 只具有 `open` 和 `disposed` 两种状态。`dispose()` 会先将状态设为 `disposed`，然后释放工具和 Provider Fiber。

但正在执行的操作可能已经通过准入检查，并在某次异步 `super.stat()` 或其他操作中等待。此时调用 `dispose()`，不能保证它随后不会继续完成文件修改。

此外，`dispose()` 捕获 Fiber 释放异常后仍返回表示已 disposed 的收据，没有单独表达“资源清理是否已确认”。

这与 #765 中较完整的 `ACTIVE → DRAINING → RELEASED / TERMINATION_UNCONFIRMED` 生命周期设计存在差异。

需要明确区分：

- 拒绝新操作：当前实现已经具备基本机制。
- 已进入的操作排空或终止：尚未证明。
- 资源释放确认：当前返回值不足以独立证明。

我不认为这里一定需要重新设计一套 Scope Manager。可以让 FS Binding 只负责拒绝新请求，将 in-flight 计数、排空和释放确认交给上层已有的 Binding/Execution 生命周期管理。

但必须明确责任边界，并添加“操作已进入、此时 Stop/dispose”的竞态测试。

还有一处将来接线时必须注意：FS Binding 的 `record(fact)` 回调异常会被捕获并忽略。这对可选诊断日志可以接受，但绝不能将这个回调直接当作 S1 的必需持久化通路。

裁决：#796 的 FS 模块可以继续修复和测试；在生命周期语义未补齐之前，不允许用它替换生产受管 FS 路径。

### 4. 中高优先级：UTE-0 的机器门禁还不是完整的发布授权机制

\#793 已经将退役条件从文字变成机器可检查的四条件谓词，这是进步。但检查源代码发现两项限制：

其一，`scripts/ute-retirement-gate.mjs` 主要通过 Git 跟踪状态及文件内的预期 token 判断证据是否存在。它没有证明证据对应当前版本、实际生产组合和完整工具族。

其二，语义差异的批准文件只要求包含 `approval.by` 指定的名字。这能够核验记录格式，却不能独立证明批准确实由有权的 Owner 作出。

因此它当前更准确地说是退役证据一致性检查器，还不是独立可信的退役授权器。

不需要为此开发复杂的签名系统。我的建议是先利用已有的 PR Review、受保护分支与 CI 记录，建立明确的 Owner 批准引用，并让 UTE-4 的实际删除 PR 必须触发该检查，而不是仅在开发者主动运行脚本时检查。

这个问题同样不阻塞 UTE-1、UTE-2 的隔离开发，但阻塞真正的 UTE-4 退役。

## 四、是否需要暂停开发？我的具体裁决

| 工作                           | 建议        | 理由                          |
| ---------------------------- | --------- | --------------------------- |
| #795 Settlement Writer       | 继续修复，暂不合并 | API 合同需要对齐；当前 CI 仍不全绿       |
| #796 Native FS Binding       | 继续修复，暂不合并 | 必须修复正式构建错误，并明确生命周期边界        |
| UTE-3 旧工具族盘点、Golden Baseline | 允许继续      | 只读研究和基线建立不会改变生产权威           |

我建议安排一次范围很窄的设计修订，而不是重开整套 UTE 架构讨论。它应该只解决四个问题：FS Family 的完整退役单位、SettlementStore 与 Writer Adapter 的关系、Binding 的 in-flight/drain 责任，以及退役证据与 Owner 批准的实际验证方式。

不应因此重新设计 ToolsService、ControlService、权限编译器或整个测试框架。

## 五、最后的总体评价

现阶段的开发速度是积极的：从测试基础清理进入 UTE-0 合同、UTE-1 产品 Binding、UTE-2 Settlement Store，已经产生了实质性的代码，而且目前还没有触及生产 Authority 或删除旧执行链。

但这轮代码审查也说明：工程实现已经开始跑到合同设计的前面。 尤其是 UTE-0 已合并为实施合同，UTE-1/UTE-2 却仍存在接口与生命周期上的未收口差异。如果继续直接推进 UTE-3 的生产接线，很可能重演 Alpha.5/Alpha.6 中边实现、边发现权威和生命周期问题的返工过程。

因此，我建议的管理动作是：

不叫停整个开发团队，但暂时停止向下一阶段扩张。先要求执行端修复 #795/#796 的现有问题，并完成上述四项有限合同修订。通过后再授权生产接线。

这样既不会浪费已经取得的 PoC 和工程基础成果，也能够在真正产生架构迁移成本之前，关闭目前已经明确暴露的问题。
