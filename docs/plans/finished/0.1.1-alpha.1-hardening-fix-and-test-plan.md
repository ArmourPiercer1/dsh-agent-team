# 3. P0-1：unresolved template 必须 fail closed

## 3.1 问题

当前 live glue 存在以下危险回退：

```text
blueprint unavailable
OR member instance 无法解析
OR templateId 缺失
OR templateId 在 blueprint 中不存在

→ { mode: 'legacy' }
```

这会把 identity/template resolution failure 误当成“真正 legacy template”，进而恢复到完整旧行为：

```text
full Team-tool catalog
no built-in deny
legacy MCP path
```

这是权限 fail-open。

真正的 legacy 只能定义为：

```text
成功定位到 BlueprintTemplate
AND template.capabilities === undefined
```

其他解析失败必须阻断 Agent setup。

## 3.2 目标语义

推荐引入明确三态/两层返回值：

```ts
type StaticCapabilityResolution =
  | {
      status: 'resolved'
      capabilities: StaticTemplateCapabilities
    }
  | {
      status: 'unresolved'
      reason:
        | 'blueprint-unavailable'
        | 'member-instance-unresolved'
        | 'template-id-missing'
        | 'template-not-found'
    }
```

若不希望新增类型，也可用 typed exception，但行为必须相同：

```text
Leader:
  成功解析 blueprint.leader
  → selective / true legacy

Member:
  成功解析 durable instance → templateId → member template
  → selective / true legacy

任何 identity/template resolution failure
  → typed setup failure
  → unpublished Agent rollback
  → no live residency
```

## 3.3 Error contract

建议稳定错误码：

```text
capability-template-unresolved
```

错误信息至少携带：

```text
sessionId
instanceId?
templateId?
reason
```

不要把 unresolved 映射成 legacy。

## 3.4 Fresh-create hint

`templateIdHint` 只能用于 fresh-create 明确存在的创建窗口；不能成为 cold resume 或普通 request boundary 找不到 durable identity 时的授权 fallback。

建议冻结：

```text
fresh-member:
  仅当生命周期契约明确允许 hint 时使用

cold-member / request-boundary:
  durable identity 必须存在
  missing → fail closed
```

若当前 fresh-create 在 Agent setup 前已经写入 durable row，则直接删除对 hint 的授权依赖。

## 3.5 测试

至少新增：

```text
U1 真正 legacy：template 存在，capabilities absent → legacy behavior
U2 templateId 不存在：setup rejects；no live member；no Team tools
U3 cold-resume member row missing：fail closed
U4 Leader blueprint unavailable：前置流程或 setup fail closed
U5 sibling isolation：A unresolved 不得把 B 降级成 legacy
```

# 4. P0-2：保存并调用真实 tools.restrict disposer

## 4.1 问题

当前 adapter 将 seam 建模成：

```ts
restrict(opts): void
```

并返回 no-op disposer。

真实 upstream public seam 是：

```ts
restrict(filter): () => void
```

返回的函数就是解除 restriction 的 exact disposer。

当前实现虽然可能在 Agent scope 整体销毁时“看起来能工作”，但破坏了 explicit cleanup、adapter 自己的生命周期契约，也会让后续 dynamic tighten/loosen 无法安全复用。

## 4.2 修复实现

建议：

```ts
export function applyBuiltInToolDeny(
  agentCtx: {
    tools: {
      restrict: (opts: { deny: string[] }) => () => void
    }
  },
  deniedNames: readonly string[],
): ToolRestrictionDisposer {
  const uniqueDenied = [...new Set(deniedNames)]

  if (uniqueDenied.length === 0) {
    return { dispose() {} }
  }

  const lift = agentCtx.tools.restrict({ deny: uniqueDenied })
  let disposed = false

  return {
    dispose() {
      if (disposed) return
      disposed = true
      lift()
    },
  }
}
```

要求：

```text
empty deny → restrict never called
dedup preserve first-seen order
dispose idempotent
upstream disposer exactly once
```

若 live close 已统一 best-effort 捕获 disposer 异常，不必在 adapter 重复吞异常。

## 4.3 测试

```text
D1 deny=[] → zero restrict calls
D2 ['bash','bash','write'] → restrict(['bash','write'])
D3 dispose → upstream disposer called once
D4 double dispose → still once
D5 live close path → restriction disposer actually invoked
```

# 5. P0-3：调整 Agent setup ordering

正确顺序冻结为：

```text
1. model selection
2. agentPresets.mount(...)
3. applyBuiltInToolDeny(...)
4. Team tool scoped registrations
5. Team skill scoped registrations
6. MCP composition / reconcile
```

原因：`tools.restrict()` 限制的是 Agent 从父/global scope 继承的工具，而同一 Agent scope 自己注册的工具保持 visible。

这正好符合目标：

```text
builtinToolDeny
→ mask preset base tools

teamTools
→ independently governed by teamTools allowlist
```

禁止：

```text
builtinToolDeny 同时变成 Team-tool deny
通过重写 Team catalog 规避 preset restriction
```

测试至少构造：

```text
preset inherited: read/write/edit/bash
Team scoped: team_delegate/team_send_message
```

配置：

```yaml
builtinToolDeny:
  - bash
  - write
teamTools:
  kind: allow
  items:
    - team_delegate
```

验收：

```text
read visible
edit visible
bash hidden
write hidden
team_delegate visible
team_send_message absent
builtinToolDeny 不得隐藏 team_delegate
```

# 6. P1：allow([]) 必须保留显式策略值

## 6.1 问题

当前 `selectiveToTemplatePolicyValues()` 会省略：

```ts
allow(items: [])
```

这会把“显式空 allow”误解释成 unspecified，从而可能让低优先级 Blueprint / PolicyState 获胜。

## 6.2 正确语义

只要 template capabilities 为 selective，以下三个字段都必须进入 `TemplatePolicy.values`：

```text
teamTools
skills
mcp
```

即使是：

```text
allow([])
```

建议直接：

```ts
values.tools = capabilities.teamTools
values.skills = capabilities.skills
values.mcp = capabilities.mcp
```

只有真正 legacy 才返回 empty/undefined template authority。

## 6.3 测试

```text
E1 teamTools allow[] → values.tools 显式存在
E2 skills allow[] → values.skills 显式存在
E3 mcp allow[] → values.mcp 显式存在
E4 Blueprint allow[A,B] + Template allow[] → effective allow[]
E5 provenance winner = Template，而不是 lower layer
```
