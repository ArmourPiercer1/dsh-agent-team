# `0.1.1` Alpha 路线备忘：从 Capability Wiring 到完整权限治理

> **状态：冻结的版本边界备忘。**
>
> 本文用于替代此前将大量 capability wiring、参数级权限、动态治理、hard boundary、Remote/UI 等内容一次性塞入 `0.1.1-alpha.1` 的开发文档。
>
> 核心原则：**每个 alpha 都必须产生用户可感知、可验证的能力增量；最后一个 alpha 完成原先“大 alpha.1”中已经冻结的完整权限治理目标。**

---

## 1. 总体目标

当前仓库已经具备大量后端 primitive：

- Blueprint / TeamSession / MemberTemplate / MemberInstance；
- generic capability policy (`model / tools / permissions / skills / mcp`)；
- `PolicyEntry = allow(items) | deny`；
- policy precedence / overlay / mutation 基础设施；
- AgentSetup / binder / live Agent create-resume-reconcile；
- Agent-scoped tool / skill / MCP public seams；
- durable control request / decision / exact-once guard；
- model durable selection；
- MCP durable facet；
- external hard facts；
- operation journal。

因此 `0.1.1` 不再按“从零搭建授权系统”推进，而按四层能力递进：

```text
alpha.1   给谁装什么
          Capability Materialization

alpha.2   这个具体操作能不能做
          Static Operation Authorization

alpha.3   谁能改变未来权限
          Dynamic Governance

alpha.4   哪些边界 Agent 自己永远不能越过
          Hard Governance
```

四个阶段均保持：

```text
CORE PATCH BUDGET = 0
public seams only
no private DSH registry
no upstream source patch
```

# 2. `0.1.1-alpha.1`
## Capability Wiring + Built-in Tool Blacklist

### 2.1 版本目标

实现：

> **针对不同 Leader / MemberTemplate / MemberInstance，实际获得不同的 Team tools、Team-managed skills、Team MCP，并能够在 Agent scope 黑名单禁用 DSH/base preset 继承来的内建工具。**

这是第一个真正具有“职责隔离”意义的版本。

### 2.2 Template 声明

建议最小形式：

```yaml
members:
  - templateId: researcher
    capabilities:
      teamTools:
        kind: allow
        items:
          - team_send_message
          - team_list_members

      builtinToolDeny:
        - bash
        - write
        - edit

      skills:
        kind: allow
        items:
          - research

      mcp:
        kind: allow
        items:
          - research-mcp
```

其中：

- `teamTools`：沿用 `allow(items) | deny`；
- `builtinToolDeny`：精确工具名黑名单；
- `skills`：沿用 `allow(items) | deny`；
- `mcp`：沿用 `allow(items) | deny`。

### 2.3 Team tools

`teamTools.allow(items)`：

- 只注册 allow-list 中存在的 Team tool；
- Team tool catalog 仍由现有 `createTeamTools()` 产生；
- 不复制第二份 tool definition。

`teamTools.deny`：

- 给该 Agent 注册 0 个 Team tools。

### 2.4 Built-in tool blacklist

使用已经验证的 Agent-scoped public seam：

```text
agentCtx.tools.restrict({ deny: [...] })
```

目标：

```text
researcher:
  deny bash/write/edit

coder:
  deny []

reviewer:
  deny bash/write/edit
```

黑名单必须实际影响 Agent 可见/可调用工具，而不是仅作为 metadata。

本阶段只做：

```text
exact tool-name deny
```

不做：

```text
built-in tool allow-list
path matching
argument matching
ask
parameter permission
```

### 2.5 Skills

只管理 **Team-managed skills**：

```text
Template skills policy
        ↓
TeamSkillCatalog
        ↓
agent.ctx.get('skills').register(...)
```

不试图隐藏 DSH 或其他插件已经全局继承的 skill。

### 2.6 MCP

按 teammate 决定 MCP mount。

最低要求：

- 当前 production 只有一个 configured Team MCP server 时：
  - allow-list 含 serverName → mount；
  - deny / allow-list 不含 → 不 mount。
- 若现有生产结构天然支持多个 server，可逐 server filter；
- 不为了 alpha.1 新建完整 MCP administration/catalog subsystem。

### 2.7 Legacy

旧 Blueprint 不包含 `capabilities`：

> 完全维持 `0.1.0-rc.1` 行为。

不能因为新 policy 默认 fail-closed 导致旧 Team 的 tools / MCP 突然消失。

### 2.8 本阶段不做

```text
parameter-level permission
allow/ask/deny operation rules
pre-execute approval
allow_once
grant_instance
dynamic permission mutation
teamHardDeny
Human hard override
permission administration UI
async approval
```

### 2.9 用户可感知变化

可以实际配置：

```text
researcher
- 可使用 read/glob/grep 等未被 deny 的基础工具
- 禁用 bash/write/edit
- 只得到 researcher 所需 Team tools
- 得到 research skill
- 得到 research MCP

coder
- 保留 coding 所需内建工具
- 得到 coding Team tools
- 得到 coding skill/MCP

reviewer
- 禁用 bash/write/edit
- 只得到 review Team tools/skills
- 不挂载 MCP
```

这是“权限限制开始真实有效”的最小版本。

# 3. `0.1.1-alpha.2`
## Static Parameter-Aware Permissions + Synchronous Approval

### 3.1 版本目标

解决 alpha.1 无法处理的问题：

> “有 `read` 不代表可以读整个文件系统；有 `write` 不代表可以写任意位置。”

### 3.2 新权限模型

加入：

```text
allow
ask
deny
default = ask | deny
```

只做静态规则，不做动态 mutation。

### 3.3 第一批受控工具

Release MUST：

```text
read
write
edit
```

低成本则加入：

```text
read_image
lsp
```

Bash：

```text
parameter-level ask / deny
```

不做 Bash strong positive allow。

MCP：

```text
仍只 server/tool-name level
```

不做 MCP argument rules。

### 3.4 Canonical Operation

建立：

```text
ToolCall
→ canonical security-relevant operation
→ deterministic fingerprint
```

最低 fingerprint：

```text
read
  canonical resource
  offset
  limit

write
  canonical resource
  content hash

edit
  canonical resource
  old_string hash
  new_string hash
  replace_all
```

支持其他工具时补齐其 side-effect/security-relevant fields。

### 3.5 参数 matcher

只使用小而确定的 typed grammar。

目标形态：

```text
exact
subtree
any
```

但：

- `subtree` 只有在 public filesystem seam 可以安全证明 descendant relation 时实现；
- 不能解析 opaque private `targetKey`；
- 若 public seam 不足，则 alpha.2 先发 `exact | any`。

不接受：

```text
glob
regex
opaque DSL
boolean expression
```

### 3.6 Synchronous approval

```text
Teammate operation
→ ask
→ Leader
   ├ allow_once
   └ deny
```

Leader 自己：

```text
Leader ask
→ Human
```

Leader 不得 self-approve。

### 3.7 `allow_once`

批准的是：

> **具体 operation + concrete impact**

不是“对同一资源的一次任意访问”。

因此 changed payload / changed resource 不能消费旧批准。

### 3.8 External hard

最后 dispatch 前重新检查 live external hard。

旧 approval 不能穿透后来收紧的 host/system restriction。

### 3.9 本阶段不做

```text
dynamic mutation
grant_instance
durable grants
teamHardDeny
Leader proactive permission administration
permission CAS snapshots
runtime permission delta inject
full Permission UI
async approval/retry
```

### 3.10 用户可感知变化

例如：

```text
researcher:
  read D:/project/** → allow
  write D:/project/output/result.json → ask
  write D:/project/src/** → deny

coder:
  edit D:/project/src/** → allow
  read D:/project/secrets/** → deny
```

权限从“工具级”进入“具体操作级”。

# 4. `0.1.1-alpha.3`
## Dynamic Permission Governance

### 4.1 版本目标

让运行中的 Team 可以安全地改变未来权限。

核心问题：

> **谁有权修改谁的 permission state？**

### 4.2 Self-frozen authority

冻结：

```text
Human
  ↓
Leader governance authority / mutationEnvelope
  ↓
Teammate permission state
```

Teammate：

- 可以执行允许操作；
- 可以触发 ask；
- 可以拒绝使用某工具；
- 可以请求权限变化；

但不能持久修改约束自己的：

```text
allow
ask
deny
default
mutationEnvelope
```

即使是 self-tightening，也不作为 alpha.3 的成员自写入口。

### 4.3 Leader proactive mutation

Leader 可以在 frozen `mutationEnvelope` 内修改下属普通权限：

```text
allow ↔ ask ↔ deny
```

但：

- 不能改变约束自己的 governance ceiling；
- 不能越过 external hard；
- 不能为自己 self-approve。

### 4.4 Durable permission snapshots

权限 mutation：

```text
read current complete snapshot
→ merge intended change
→ append new complete snapshot
```

alpha.3 使用完整 per-layer snapshot，不引入 per-rule event-sourcing DSL。

### 4.5 `grant_instance`

新增：

```text
allow_once
grant_instance
deny
```

其中：

```text
grant_instance
=
ControlDecision(ALLOW) for current blocked operation exactly once
+
durable exact-resource future grant
```

例：

```text
Write(D:/project/output/result.json)
```

grant 后：

- 当前 write 继续；
- 同 MemberInstance 对 exact resource 的未来对应操作获得 durable grant；
- `result2.json` 不自动继承。

### 4.6 Runtime visibility

正式实现：

```text
durable truth
+
runtime current permission snapshot
+
agent.inject(permission-change notice)
```

不回滚已经 commit 的 durable truth，仅因 inject 失败而回滚。

Future boundary：

```text
Step N starts with P0
mutation during Step N
Step N stays P0
Step N+1 sees P1
```

### 4.7 Lifecycle

```text
RUNNING → ARCHIVED
grant remains durable, no execution

ARCHIVED → RESTORE → RUNNING
same MemberInstance grant effective again

DISPOSED
grant permanently loses effective authority
audit record may remain
```

### 4.8 用户可感知变化

Team 可以逐步授权：

```text
researcher initially read-only
→ asks for one output file write
→ Leader grant_instance
→ future same-resource writes no longer ask
```

而不是启动时一次性开放整个目录或工具。

# 5. `0.1.1-alpha.4`
## Hard Governance + Complete Original Permission Target

### 5.1 版本目标

补齐普通治理和 Agent 不可自行突破的 hard governance boundary。

alpha.4 完成后：

> 达到此前“大 alpha.1”已经冻结的完整权限治理目标。

### 5.2 `teamHardDeny`

加入独立 hard lane：

```text
ordinary allow
ordinary ask
ordinary deny
teamHardDeny
externalHard
```

层级：

```text
External Hard
      ↑
Human
      ↑
Team Hard Boundary
      ↑
Leader mutationEnvelope
      ↑
Teammate current permission
```

### 5.3 普通 deny

普通 `deny`：

- 当前 operation 终止；
- 不自动 ask；
- 更高合法 Team governance layer 可事先覆盖较低层 ordinary deny。

若规则必须 Leader 无法自行越过：

```text
使用 teamHardDeny
```

### 5.4 Teammate hard-deny flow

```text
Member operation
→ teamHardDeny
→ block
→ Leader review
   ├ deny
   └ escalate_to_user
        → Human
```

Leader：

- 不能 allow_once 穿透；
- 不能 grant_instance 穿透；
- 只能 deny 或 escalate。

### 5.5 Leader own hard deny

```text
Leader operation
→ teamHardDeny
→ Human
```

禁止 Leader self-approve。

### 5.6 Human hard override

Human 可以显式突破 Team hard boundary。

但：

```text
Human cannot bypass externalHard
```

hard-bypass 必须有独立 provenance，不能伪装成普通 allow。

### 5.7 Complete governance surface

此阶段再完整补：

```text
permission rules view
defaults
ordinary deny
teamHardDeny
mutationEnvelope
instance grants
pending approvals
provenance
legal actions
Remote/API versioning
Permission Administration UI
```

### 5.8 完整安全矩阵

至少覆盖：

```text
fresh create
cold resume
tighten
loosen
archive/restore
dispose
exact allow_once
payload mismatch
exact durable grant
Leader proactive mutation
Member self-mutation rejection
teamHardDeny
Leader hard review
Human hard override
external-hard drift
cross-instance isolation
```

# 7. 明确不属于这四阶段完成条件的内容

此前已明确撤回的异步 Human approval 不计入“大 alpha.1”冻结完成条件：

```text
async Human wait
Agent continues unrelated work
later result injection
retry payload equivalence
changed payload impact comparison
```

未来单独设计。

# 8. Release philosophy

每一版只有一个主问题：

```text
alpha.1
Capability Materialization

alpha.2
Operation Authorization

alpha.3
Dynamic Governance

alpha.4
Hard Governance
```

任何后续阶段的问题：

> 不得阻塞前一阶段发布。

任何 alpha 中发现的非本阶段必要能力：

> 进入下一阶段 backlog，不触发重新设计整个路线。
