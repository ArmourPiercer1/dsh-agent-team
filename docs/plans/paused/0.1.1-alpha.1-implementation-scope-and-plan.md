# `0.1.1-alpha.1` Implementation Scope and Delivery Plan

- **Repository:** `ArmourPiercer1/dsh-agent-team`
- **Target release:** `0.1.1-alpha.1`
- **Current product baseline:** `0.1.0-rc.1` frozen by project decision
- **Repository baseline observed during planning:** master around `3be0de1f0e56f37db85e83334f361d401e1e70c6`
- **Core constraint:** `CORE PATCH BUDGET = 0`
- **Related design:** `permission-system-design-0.1.1-alpha.1.md`
- **Related ADR:** `ADR-001-hierarchical-self-frozen-permission-governance.md`

## 1. Release goal

The release goal is to turn the existing abstract capability-policy architecture into a real production path:

```text
Blueprint
→ per-Template policy
→ per-MemberInstance override
→ effective capability resolution
→ AgentSetup
→ live Agent capability
```

The release should make the following capability domains materially affect the live Agent:

- `tools`
- `skills`
- `mcp`
- `permissions`

`model` should remain on the existing live model-selection path and be regression-tested as part of the unified resolution pipeline, but does not need a new model-selection architecture in this release.

The release also upgrades `permissions` from whole-cell allow/deny to the parameter-aware governance model defined in the design document.

## 2. Explicit non-goals

Do not add the following to `0.1.1-alpha.1`:

- separate `AGENTS.md` injection;
- generic arbitrary predicate DSL;
- multi-parameter permission conjunctions;
- Bash command-pattern positive allow;
- MCP parameter-level permissions;
- approval-dialog custom-scope policy editing;
- approval-derived Template-wide or Team-wide grants;
- asynchronous Human approval/retry;
- payload-equivalence/impact-equivalence analysis;
- DSH core patches;
- replacement of DSH tool/session/MCP/skill public seams;
- large Policy Administration UI.

## 3. Current gaps that the release must close

### 3.1 Production Blueprint/template capability declarations are incomplete

The current production Blueprint/template surface does not yet fully expose the per-template capability declarations needed for:

```text
tools
permissions
skills
mcp
```

The release must make these first-class Template policy inputs.

### 3.2 Production policy reader is not yet a real per-template source

Any placeholder/empty `readTemplatePolicy`-style production path must be replaced with policy derived from the bound Blueprint snapshot and concrete MemberTemplate.

### 3.3 Generic permission cell is insufficient

The current `PolicyEntry` shape is whole-cell:

```ts
allow(items)
deny
```

The parameter-aware permission system requires a dedicated typed `PermissionPolicy`.

### 3.4 Mutation actor and scope are too tightly coupled

The existing conceptual mapping:

```text
leader → template overlay
member → instance overlay
```

does not support the new permission authority model.

For permissions, alpha requires:

```text
Leader origin → MemberInstance permission overlay
Member origin → forbidden
Human origin → instance override for approval-derived grant
```

### 3.5 Control scope does not bind arguments/resource identity

The current control-plane scope must be extended so one approval cannot authorize a different path/payload.

### 3.6 Tool/skill/MCP resolution is not yet fully consumed by AgentSetup

The policy layers exist conceptually, but live production Agent setup must actually:

- restrict/expose tools;
- register/unregister skills;
- mount/unmount permitted MCP surfaces;
- reconcile changes on future request boundaries.

### 3.7 Permission mutation is not yet model-visible as a live governance event

The affected Agent needs:

- current permission truth in runtime context;
- `agent.inject` delta notification on live mutation.

## 4. Proposed implementation workstreams

The workstreams below are ordered by dependency, not by repository module ownership.

---

## Workstream A — Typed capability policy model

### Goal

Make `permissions` a typed domain without destabilizing the other four capability domains.

### Tasks

1. Introduce `PermissionPolicy`.
2. Add:
   - `default: 'deny' | 'ask'`;
   - ordinary `allow`;
   - ordinary `ask`;
   - ordinary `deny`;
   - `teamHardDeny`.
3. Define a typed permission-rule/matcher representation suitable for one primary security parameter.
4. Keep `model/tools/skills/mcp` on the current generic entry representation unless a small common wrapper is needed.
5. Update validation and normalization.
6. Update deep-freeze/lossless-JSON validation.
7. Preserve provenance fields.
8. Version any DTO/contract surface that currently assumes all five domains have identical value shapes.

### Acceptance

- malformed permission policy fails closed;
- generic capabilities continue to pass existing tests;
- no permission rule is encoded as an unvalidated opaque mini-language solely to avoid changing the type system.

---

## Workstream B — Blueprint and Template capability declarations

### Goal

Make the Blueprint snapshot the authoritative static source of per-template capability policy.

### Tasks

1. Extend MemberTemplate/Blueprint schema to carry:
   - tools;
   - permissions;
   - skills;
   - mcp;
   - existing model selection/preference as appropriate.
2. Keep Blueprint Team autonomy/governance envelope distinct from Template current values.
3. Define Template `permissions.default`.
4. Parse and freeze all capability declarations.
5. Replace any production placeholder template-policy reader with real Blueprint/template lookup.
6. Ensure multiple MemberInstances created from one Template resolve the same static baseline but separate instance overlays.

### Acceptance

- two templates with different capability declarations produce different effective configs;
- two instances of the same template share static baseline but not durable instance grants;
- invalid Blueprint permission syntax prevents unsafe activation.

---

## Workstream C — Unified per-instance effective capability resolution

### Goal

Produce one explainable effective capability view for each MemberInstance.

### Tasks

1. Retain existing generic resolver behavior for:
   - model;
   - tools;
   - skills;
   - mcp.
2. Add a dedicated operation-local permission resolver for `permissions`.
3. Keep these ordinary permission layers:
   - Blueprint;
   - PolicyState;
   - Template;
   - TemplateOverlay;
   - InstanceOverlay;
   - HumanOverride.
4. Add the separate accumulated Team hard-deny lane.
5. Apply external hard facts after/beside Team resolution as defined by the permission design.
6. Preserve provenance and suppression history.
7. Continue using future-boundary captures for in-flight work.

### Acceptance

- every effective capability has explainable source/provenance;
- permission decisions identify the matching layer/rule;
- same-layer ordinary conflict is `deny > ask > allow`;
- higher ordinary layer may override lower ordinary deny;
- ordinary policy never bypasses Team hard deny.

---

## Workstream D — Tools live wiring

### Goal

Make effective `tools` policy change the actual live Agent tool surface.

### Tasks

1. Reuse DSH Agent-scoped tool APIs:
   - `agentCtx.tools.register(...)`;
   - `agentCtx.tools.restrict(...)`;
   - `agentCtx.tools.schemas(agent)` where needed.
2. Preserve ordinary preset/base-tool mounting.
3. Apply Team tool restrictions **after** the base substrate is mounted so policy can hide inherited tools.
4. Ensure per-Template/per-Instance tool resolution is respected on:
   - fresh create;
   - cold resume;
   - future-boundary policy change.
5. Ensure hidden tools do not leak through another registry path.
6. Keep Team tools and ordinary file/shell tools conceptually distinct where the current runtime already does so.

### Acceptance

- tool visible in Template A and denied in Template B behaves accordingly;
- instance overlay can lawfully alter tool availability within governance rules;
- cold resume reconstructs the same tool surface;
- no global tool registry mutation affects sibling Agents.

---

## Workstream E — Skills live wiring

### Goal

Make effective `skills` policy control the actual Agent-scoped skill set.

### Tasks

1. Add/normalize a production skill catalog abstraction.
2. Resolve policy item IDs to concrete skill definitions.
3. Register allowed skills with Agent-scoped registration.
4. Dispose/unregister skills when future-boundary policy removes them.
5. Reapply on cold resume.
6. Fail closed if a policy names a skill that is required but unavailable, according to the chosen capability-existence semantics.
7. Keep the skill catalog separate from permission logic.

### Acceptance

- Template A/B can receive different skill sets;
- per-instance policy can affect live skills;
- removing a skill takes effect at the documented future boundary;
- restart restores the same effective skill set.

---

## Workstream F — MCP live wiring

### Goal

Make effective `mcp` policy control Agent-scoped MCP mounts.

### Tasks

1. Reuse the existing Agent-scoped `agentCtx.plugin(mcpClient, ...)` seam.
2. Introduce a minimal MCP catalog/facade rather than baking policy semantics permanently around one singleton config.
3. For alpha, the current 0-or-1 configured MCP server may be adapted into that catalog if necessary; multi-server UI is not required.
4. Resolve per-Template/per-Instance MCP policy.
5. Mount allowed MCP server(s) during AgentSetup.
6. Unmount on future-boundary policy removal.
7. Reapply on cold resume.
8. Preserve fail-closed startup behavior.
9. Do not implement parameter-level MCP rules.

### Acceptance

- an instance with denied MCP has no MCP mount;
- an allowed instance gets the scoped mount;
- tightening removes the mount before the next governed operation;
- cold resume reconstructs policy-consistent MCP state;
- MCP failures do not leave a half-mounted capability.

---

## Workstream G — Parameter-aware permission adapters

### Goal

Enforce concrete operation permissions through the DSH pre-execution seam.

### Tasks

1. Add a permission adapter registry internal to Team for supported built-ins.
2. File adapters:
   - `read(file_path)`;
   - `read_image(file_path)`;
   - `write(file_path)`;
   - `edit(file_path)`;
   - `lsp(file_path)`.
3. Resolve paths using the DSH public filesystem resolver.
4. Produce canonical resource identity.
5. Bash adapter:
   - support `ask/deny/teamHardDeny`;
   - no strong parameter allow.
6. MCP:
   - no parameter adapter.
7. Add operation fingerprint generation.
8. Add structured decision diagnostics/provenance.
9. Install enforcement via `tools/pre-execute`.

### Acceptance

- relative/path-alias forms cannot bypass policy;
- denied path never reaches DSH tool dispatch;
- ask path enters control;
- allowed path reaches dispatch;
- unsupported adapter fails according to a documented conservative rule.

---

## Workstream H — Permission authority and mutation service refactor

### Goal

Implement the self-frozen governance hierarchy.

### Tasks

1. For `permissions`, reject direct Member-origin mutation at the authority boundary.
2. Support Leader-origin InstanceOverlay.
3. Keep Leader mutation bounded by the Member governance `mutationEnvelope`.
4. Make `mutationEnvelope` immutable to the Leader it constrains.
5. Restrict `teamHardDeny` governance to static/Human authority.
6. Support Human instance-scoped exact-resource override.
7. Keep broader Human Team/Template policy administration out of the approval flow.
8. Store complete permission snapshots per mutated layer.
9. Preserve append-only mutation ledger/provenance.
10. Ensure restrictive and expansive mutations are both governance operations and both require the correct higher authority.

### Acceptance

- Member cannot self-grant;
- Member cannot self-deny persistently;
- Leader can proactively modify a Member's ordinary permission state inside envelope;
- Leader cannot modify its own envelope;
- Leader cannot mutate away Team hard deny.

---

## Workstream I — Control plane and approval upgrades

### Goal

Bind synchronous approval to the exact concrete operation and implement the new grant semantics.

### Tasks

1. Extend `ControlOperationScope` with:
   - canonical resource or equivalent security identity;
   - operation fingerprint.
2. Keep correlation/request identity.
3. Preserve exact-once consumption.
4. Member ordinary `ask` routes to Leader.
5. Leader own `ask` routes to Human.
6. Enforce no Leader self-approval.
7. For a Member Team hard-deny hit:
   - create Leader review;
   - allow only `deny` or `escalate_to_user`;
   - create/link `USER_APPROVAL` on escalation.
8. Do not overload an ordinary `LEADER_APPROVAL` path in a way that lets Leader authorize through hard deny.
9. Implement `grant_instance` as:
   - ControlDecision allow for current call;
   - durable exact-resource permission mutation for future calls.
10. Human approval-derived durable grant is also instance+exact-resource.
11. Recheck live external hard at final dispatch.
12. Clarify/rename `envelope-mutation` vocabulary:
   - mutation **inside** an envelope may be Leader-authorized;
   - mutation **of** the Leader envelope is Human authority.

### Acceptance

- changed resource cannot consume an old approval;
- one-shot allow cannot be consumed twice;
- current call succeeds on `grant_instance`;
- subsequent exact resource succeeds without asking;
- sibling resource does not inherit the grant;
- hard-deny escalation cannot be authorized by Leader.

---

## Workstream J — Model-visible permission state and live notification

### Goal

Prevent execution-flow confusion when Leader/Human changes a live Agent's permissions.

### Tasks

1. Add a runtime-context permission snapshot to the Agent's model-visible context.
2. Recompute/reconcile it from durable truth at request/model boundaries.
3. On a live permission mutation, call `agent.inject(...)` with a concise delta notice.
4. Keep the durable state authoritative.
5. Ensure mutation becomes model-visible no later than its effective boundary.
6. Handle:
   - live Agent;
   - idle live Agent;
   - cold resume;
   - crash after commit/before inject.
7. Avoid injecting a huge full rule list each time; use a concise current-state summary plus delta.

### Acceptance

- grant/revoke is visible to the affected Agent at the next effective model step;
- crash/restart still exposes correct current permission state without relying on a lost inject;
- an in-flight captured step is not silently reinterpreted.

---

## Workstream K — Lifecycle integration

### Goal

Make instance-scoped capability and permission state obey MemberInstance lifecycle.

### Tasks

1. `ARCHIVED`:
   - no new work;
   - retain durable instance overlays.
2. `RESTORE`:
   - reapply same instance policy/capabilities.
3. `DISPOSED`:
   - terminate effective instance-local grants/capabilities;
   - retain audit history.
4. Ensure live tool/skill/MCP side effects are disposed with the Agent/lifecycle path.
5. Ensure restoration re-runs AgentSetup/reconciliation from durable truth.

### Acceptance

- archive blocks execution;
- restore recovers prior exact grants and capability set;
- dispose cannot accidentally transfer grants to a replacement/new instance.

---

## Workstream L — Remote/UI/governance surface

### Goal

Expose enough information to operate and debug the new system without building the full future policy editor.

### Tasks

1. Extend effective-config/projection DTOs for typed permission policy.
2. Show:
   - current permission default;
   - relevant allow/ask/deny/hard rules;
   - governance envelope summary;
   - provenance;
   - pending approval state.
3. Approval UI must distinguish:
   - `allow_once`;
   - `grant_instance`;
   - `deny`;
   - `escalate_to_user` where legal.
4. Hard-deny Leader review must not render an `allow` control.
5. Human approval should allow:
   - deny;
   - allow once;
   - exact-resource durable instance grant.
6. Do not add arbitrary scope editor.
7. Rename/relabel ambiguous "envelope mutation" actions so users can tell:
   - Member policy mutation inside Leader envelope;
   - Human modification of the envelope itself.

### Acceptance

- UI never offers an action the backend authority model will reject;
- provenance identifies who changed what and when;
- no UI path permits Member self-mutation or Leader hard-deny bypass.

---

## Workstream M — Compatibility and migration

### Goal

Land the alpha changes without breaking current vNext durability assumptions.

### Tasks

1. Version the typed permission DTO/schema.
2. Define how old whole-cell permission records are interpreted:
   - conservative adapter, or
   - explicit migration/rejection with a typed compatibility diagnostic.
3. Preserve old model/tools/skills/mcp mutation records.
4. Ensure old Team sessions do not silently receive broader permission semantics.
5. Update mock/harness fixtures.
6. Keep append-only provenance readable.
7. Document the behavior boundary between `0.1.0-rc.1` and `0.1.1-alpha.1`.

### Recommended migration stance

Prefer conservative compatibility:

- old `permissions: deny` → deny/fail-closed baseline;
- old `permissions: allow(items)` should not be guessed into path-level semantics unless the old item vocabulary has an exact documented mapping;
- ambiguous legacy values should remain visible but not create new parameter-level privilege.

---

## Workstream N — Verification and evidence

### Goal

Treat the permission system as a security/governance feature, not only a UI feature.

### Required test classes

#### Domain tests

- schema normalization;
- rule matching;
- layer precedence;
- same-layer `deny > ask > allow`;
- hard-deny accumulation;
- default behavior;
- envelope containment.

#### Runtime mutation tests

- Member mutation forbidden;
- Leader instance mutation allowed in envelope;
- Leader envelope self-mutation forbidden;
- Human override;
- archive/restore/dispose.

#### Control tests

- exact operation scope;
- payload mismatch;
- exactly-once consumption;
- no Leader self-approval;
- Team hard-deny escalation;
- Human-only user approval.

#### Live seam tests

- tool visibility;
- pre-execute path gate;
- skills registration/removal;
- MCP mount/unmount;
- cold resume;
- runtime-context + `agent.inject`.

#### Race/crash tests

- permission mutation during in-flight step;
- crash after mutation commit/before inject;
- external-hard tightening between approval and dispatch;
- approval decision during target archive/dispose;
- restart with pending control request.

#### End-to-end matrix

At minimum cover:

```text
fresh create
cold resume
tighten
loosen
capability disappearance
archive/restore
dispose
Leader approval
Human approval
Team hard deny
external hard drift
```

### Evidence requirements

For the release gate, record:

- exact repository SHA;
- test command and totals;
- focused permission/control matrix;
- live tool/skill/MCP evidence;
- cold-resume evidence;
- zero-core-patch proof;
- known limitations/non-goals.

## 5. Suggested implementation order

The shortest dependency-respecting sequence is:

```text
A Typed policy model
  ↓
B Blueprint/Template declarations
  ↓
C Effective per-instance resolution
  ↓
G Permission adapters
  ↓
H Authority/mutation refactor
  ↓
I Control plane upgrade
  ↓
D Tools wiring
E Skills wiring
F MCP wiring
  ↓
J Runtime-context + inject
  ↓
K Lifecycle integration
  ↓
L UI/Remote projection
  ↓
M Compatibility/migration
  ↓
N Full verification
```

Tools/Skills/MCP can partially proceed in parallel after B/C because they share the effective capability view but have separate live seams.

## 6. Definition of Done for `0.1.1-alpha.1`

The release is ready when all of the following are true:

1. Blueprint/Template capability declarations are real production inputs.
2. Each MemberInstance resolves its own effective:
   - model;
   - tools;
   - permissions;
   - skills;
   - mcp.
3. Tools policy actually changes the live tool surface.
4. Skills policy actually changes the live Agent skill set.
5. MCP policy actually changes Agent-scoped MCP mounts.
6. Parameter-aware permissions protect at least the specified built-in file/path tools.
7. Bash cannot receive unsafe parameter-level positive allow.
8. MCP has no accidental parameter-level permission semantics.
9. Member cannot persistently mutate its own permissions.
10. Leader can govern Member permissions within a frozen `mutationEnvelope`.
11. Leader cannot self-approve or change its own governance ceiling.
12. Team hard deny is not bypassable by Member/Leader.
13. Human can explicitly override Team hard deny but not external hard.
14. `allow_once` is exact and consumed once.
15. `grant_instance` allows the current call and creates only an exact-resource future grant.
16. Current control scope binds canonical security-relevant payload identity.
17. Permission changes are runtime-context visible and injected to live Agents.
18. Future-boundary behavior is deterministic.
19. Archive/restore preserves the same instance's grants; dispose terminates their effect.
20. External hard is checked at final dispatch.
21. Cold resume reconstructs policy-consistent tool/skill/MCP/permission state.
22. Provenance explains every effective permission decision and durable mutation.
23. No DSH core patch is introduced.
24. The documented full test/evidence matrix passes.

## 7. Deferred next-after-alpha topics

Record but do not implement:

### 7.1 Asynchronous Human approval/retry

Future desired behavior:

```text
Human approval may take a long time
→ let Agent continue unrelated work
→ inject Human result later
→ Agent retries only if still needed
```

Retry semantics under consideration:

1. if retry payload is fully equivalent to the originally approved operation, allow by default;
2. if payload changed, route to Leader;
3. Leader compares original/retry payload, behavior, boundary, and impact;
4. Leader decides whether the new action remains within the original Human intent.

This needs a formal operation-equivalence and impact-diff model.

### 7.2 Broader Human policy administration

Separate governance UI/API for:

- Team-wide policy;
- Template policy;
- custom resource scopes;
- mutation-envelope changes;
- Team hard-deny administration.

### 7.3 Strong Bash allow

Only after a shell-aware semantic parser/effect model exists.

### 7.4 MCP parameter permissions

Only when there is a stable, trustworthy MCP capability/argument model worth enforcing in the client.

### 7.5 Rich rule language

Only if concrete alpha usage demonstrates that one-primary-parameter typed adapters are insufficient.

## 8. Release summary

`0.1.1-alpha.1` should not be treated as "add a few permission checks."

It is the release that closes the production path:

```text
Blueprint
→ Template/Instance policy
→ Effective capability resolution
→ AgentSetup
→ live tools/skills/MCP
→ parameter-aware permission guard
→ Leader/Human governance
→ durable provenance
```

while retaining:

```text
CORE PATCH BUDGET = 0
```

and deliberately postponing the more speculative asynchronous approval and general-purpose policy-language work.
