## 一、G1 —— 授权路径的空白字符裁剪（trim）改址缺陷

**具体问题（证据/复现）**
蓝图文档里的授权路径（allow/deny/ask 的 `path`）在**解析保存时被悄悄去掉首尾空白**，存进文档和身份哈希的是"裁剪后"的值；而运行时访问对象**保留**首尾空白（运行时 canonicalizer 实测不归一）。于是"您授权的文件"和"实际被授权/被禁止的文件"可以是两个文件。
- 现码（origin/master 复核）：`packages/domain/blueprint/src/validate.ts:239-247`（所有字符串字段的统一裁剪）、`:793`（authority envelope 匹配路径）、`:1176` + 注释 `:1173-1174`（自证"裁剪值是 A3 解析器匹配基准"——此半句已被运行时实测证伪）；身份哈希由存储文档导出（`packages/domain/blueprint/src/hash.ts`）。
- 与冻结规范直接冲突：ADR A2-3（`docs/plans/active/alpha4-permission-governance/ADR-alpha4-hard-governance.md:819`）："domain/blueprint 的解析器**不做路径规范化，也不会添加**"。
- 端到端复现（真实临时文件，非夹具）：同目录放 `secrets.env` 与 `secrets.env␠`（尾空格是合法 POSIX 文件名），作者声明 `deny exact "secrets.env␠"` → 该 deny 被裁到 `secrets.env` 上：**您想禁的文件没禁住（落进 subtree allow 照常可读），没点名的另一个文件反被禁**；镜像方向（allow 越权落点）同样成立。证据：证据 G1-DECISION-PACKAGE.md §1（探针 `probe-nrm1-path-trim` 5 条"意图腿"预期红 = 缺陷存在本身，`logs/G1-probe-run1.txt`）；债务登记 NRM-1 = high（`docs/plans/memo/post-alpha4-debt-register.md:69`），其中 6 种不同写法（干净/NBSP/U+3000/U+2028/BOM/空格）折叠成**同一个 contentHash** `sha256:429341dc…`。
- 历史来源：证据 G1-TRIM-HISTORY.md——2026-08-30 实现风格出生 → 注释升格为"仓库规范" → A1 轮被 parent 评审记为 Recorded ruling（SESSION_ROUTER_LOG :2211/:2215，批准者**不是用户**）。**用户明确裁决：未找到**（检索面 = SESSION_ROUTER_LOG 全量、ADR-alpha4、alpha4 计划集、paused 冻结文档；不排除检索面之外的口头指示）。债务登记 §4 待裁行 = C-1（登记册 `:486`）。

**用户看到什么**
您在蓝图里写的授权，可能不是系统执行的授权：含首/尾空格的路径（常见于复制粘贴）会让 deny **静默保护不了目标文件**，还会误伤同目录另一文件；allow 则可能把权限静默落到别的文件上。两种写法不同的蓝图在系统眼里是同一份合同（哈希相同）。不含空白的普通配置完全不受影响。

**推荐与备选**
- 方案「逐字存储 verbatim」（证据记录的"用户倾向方向"）：解析器不裁剪、原样存储，授权对象==访问对象，缺陷根治，且与 A2-3 一致。代价：含首/尾空白的**既有蓝图**其 contentHash 与匹配身份改变（这就是修复本身，不是附带损伤），仓库 3 处钉住裁剪的测试夹具需同步翻转（`a1-permission-policy.test.ts:326`、`a2c7-subtree-matcher.test.ts:664-672/:1522`）。
- 备选「含空白即拒」：首尾空白路径在解析期**显式报错**（内部空格路径保持完全合法，探针 C8 腿钉死）。代价：合法 POSIX 尾空格文件名从此不可声明授权，旧源文件从"可解析"变"报错"。
- 已排除（证据 §4.1）：历史口径"只 trim ASCII 空白"与"非 ASCII 即拒但 ASCII 照旧 trim"——两者都保留已证实的静默改址缺陷；"保持现状"= 缺陷存续，仅作为未裁决时的既成事实，不是修复方向。两方案共同前提：先修正失实注释，注释必须与运行时行为一致。

**修后影响**
- 用户表现：写什么就授权什么；「含空白即拒」下会看到明确报错而不是静默改址。
- 兼容与迁移：「逐字存储」下存量 padded 蓝图的哈希/修订/已持久化快照对不上（catalog 保存原文可重扫发现，`packages/domain/blueprint/src/catalog.ts:33-39`），需要一次性迁移处置；已绑定旧快照的会话仍按旧快照运行。**用户真实配置尚未扫描**——裁决前需授权一次只读盘点（本轮无授权，属缺项，见第五节(c)）。
- 长期风险：裁剪不止 path——同一裁剪覆盖全部字符串字段（id、persona、displayName 等），且 A4 Gate A 依赖"token 检查在 trim 之后"（SESSION_ROUTER_LOG :3787）；逐 path 去裁剪与全库去裁剪是两个规模，本裁决只覆盖 path 授权面。

**❓ 需要您裁决**：蓝图授权路径选**方案「逐字存储 verbatim」**还是**方案「含空白即拒」**（"继续现状裁剪"= 已证实缺陷存续，不作为修复选项），且无论选哪个，是否授权裁决前先对您的真实实例配置做一次只读盘点？

## 二、G3 —— 自定义 persona 预设被误报"人格不兼容"

**具体问题（证据/复现）**
用户使用**不在内置清单上的自定义预设**（bespoke，例如自建的 `acme-team`）创建团队时，预检探针直接判 FATAL `PERSONA_INCOMPATIBLE`；而同一个预设在真正绑定运行（bind gate 世界）却被观测为 `standard` 并**放行**——两个世界给出矛盾判决。
- 根因：上游 rc.2 的 roster 行（`AgentPresetRow`）只有 `id/isDefault/name?/description?/broken?`（`packages/preset/agent-preset-registry/src/types.ts:8`，本轮实测）——**行里没有 persona kind 字段**；客户端对未命中静态清单的 id 原样透传为 subject（origin/master `packages/client/src/model/team-intent-model.ts:476`，其 `:444-451` 注释自证这是"文档化的 fail-closed 通道"）。kind 信息不在客户端可见的任何公开 seam 里。
- 复现：探针 6/6 全绿刻画现行为（`logs/G3-repro-run1.txt`，探针未跟踪；C1-C6 逐腿见证据 G3-DECISION-PACKAGE.md §1）。树内**已有**合法的 kind 观测口（`observePersonaKind`，bind 世界在用，探针 C3/C4 实证两世界分歧）。
- 登记：D-02（`docs/plans/memo/post-alpha4-debt-register.md:360`，"用户可见（阻塞 bespoke preset）"）。唯一冻结障碍：persona 域"U5 FROZEN"句，origin/master `packages/runtime/src/plugin/s6-remote.ts:2611`（复核注：G3 包引用 `:2618`，为探针期行号）。

**用户看到什么**
您用官方内置预设一切正常；用**自建预设**时创建面板亮红「人格不兼容」，无法创建——而这个报错是误导：预设本身没问题，运行时系统其实接受它。现状是"有文档的误关"（fail-closed），不是崩溃，但把一整类用户挡在门外。

**推荐与备选**
- 推荐（证据包建议，非裁决）「服务端观测补全 R-SERVER」：探针遇到非 kind 词的 persona 时，交给已在树的观测口；观测为 `standard` → 放行，`complete` → 仍拒，未知 → 仍 fail-closed（探针 C5/C6 已证不放宽）。零 wire / 零 upstream 变更。代价：需修订当期计划冻结句 U5（persona=用户意图直通道），属冻结语义修订、必须您点头；个别既有钉测试需按新语义同步修订。
- 备选「roster 行带 kind（走公开契约）R-CLIENT-SEAM」：上游 `AgentPresetRow` 增 kind 字段。代价：CORE_SEAM_BLOCKER（需上游公开契约变更），本仓库不可自行完成，维持 D-02 登记等待。
- 明确排除的伪修法（红线）：扩充客户端词表（=伪造 kind）、`available` 恒真（=放宽兼容检查）。

**修后影响**
- 用户表现：bespoke-standard 预设从"亮红不可建"到可建；真不兼容（complete/损坏/未知预设）照旧拦住，不会出现"该拦不拦"。
- 兼容与迁移：无 wire 变更、无 upstream 改动、无存量文档迁移；probe 与 bind gate 判决趋于一致。
- 长期风险：R-SERVER 下"探针=服务端观测+用户意图"语义需写入文档，防止后续轮把它再当纯 upstream 阻塞；若裁维持现状，建议 D-02 补记"服务端观测补正在树内已可行（C3/C5 证据），U5 冻结句是唯一障碍"。

**❓ 需要您裁决**：bespoke persona 误报是裁**允许 R-SERVER（服务端观测补全并修订 U5 冻结句）**，还是**维持现状 fail-closed、等待上游 seam（R-CLIENT-SEAM）**？

## 三、G7/G5 交集 —— 超 20 条损坏记录的徽标与 dock 分歧

**具体问题（证据/复现）**
"损坏记录"= 服务端严格读取者拒读的历史控制请求行（不可裁决）。披露有**既有的封顶常数 20**：`REMOTE_CORRUPT_CONTROL_LEGS_CAP = 20`（`packages/remote/src/contracts/types.ts:537`，master 既有，非本轮新增）。
- 实码语义（origin/master `packages/remote/src/handlers/team.ts` `corruptControlLegsValue`，fix 分支复核 `:703-729`）：`corruptCount` = **全部**损坏行数（不封顶，披露正确）；列出的 `legs` = 按账本序**最旧 20 条**；超出时 `truncated=true`，UI 文案"其余损坏记录未在此列出"（`packages/client/src/ui/locales.ts:350`）。
- 本轮已修（fix 分支 `ea54120a`+`dbe029cb`）：徽标把"损坏且 pending"的行扣掉——但只认**披露出来的 ≤20 个**序号。服务端 team 级总数无封顶（`packages/runtime/src/plugin/projection-source.ts:896-917` 用 `controlRequestRowIsGovernable` 全量排除；客户端 dock 直读该服务端总数，`packages/client/src/model/team-dock-model.ts:80`"永不自行推导"）。
- 精确后果（>20 时）：第 21 条起的"损坏且 pending"行**继续计入成员徽标、却永远不可裁决**（G5 修的"幽灵待批"在截断尾部复现）；徽标总和与 dock 团队级数出现**有界分歧**（差值 = 截断尾部中 pending 且损坏的行数，≤ corruptCount−20）。边界矩阵 12/12 已钉现行为（`30024f8b`，`logs/G7-boundary-run1.txt`；**钉行为 ≠ 裁决**，OPEN 注释在码）。复现构造：账本 fixture 造 21+ 条 corrupt 行（`probe-g7` 造法，证据 §八步骤 4）。

**用户看到什么**
团队积累超过 20 条损坏待批记录后：成员徽标显示"N 项待批"，但台账里找不到、也裁决不了其中一部分——徽标**永远清不掉**；同时顶部 dock 的团队待批总数和逐个成员徽标加总**对不上**。20 条以内一切一致（本轮已修好）。

**推荐与备选**
- 推荐（证据 §4.3 建议，非裁决）：服务端按**同一无封顶法则**直接给出每个实例的"损坏且 pending 计数"，徽标直读该计数（不依赖枚举序号，与 dock 天然一致）。代价：动 wire 语义（v9 响应加/改字段），属产品裁决。
- 备选：给截断尾部加分页/游标披露，操作员可逐条处理尾部。代价：同样动 wire 语义且多一套翻页交互。
- 不修的后果即现状：徽标含不可裁决项、与 dock 有界分歧（已钉住披露）。

**修后影响**
- 用户表现：徽标只数"真能处理的"，与台账、dock 三处一致；损坏尾部要么从计数消失（方案一）要么可翻页处理（方案二）。
- 兼容与迁移：wire 契约版本语义变化，客户端/服务端需同轮升级（pre-alpha 无已发布语料，无存量迁移）。
- 长期风险：不改则任何"封顶披露 + 本地扣减"组合都会复现这类分歧；改了则"损坏行的产品定义"（计数里算不算）第一次成为成文规则。

**❓ 需要您裁决**：超过 20 条截断线的"损坏且 pending"行，是接受现状（徽标计入但永远不可裁决），还是裁"服务端无封顶 per-instance 损坏-pending 计数、徽标直读"（或加分页尾部披露）？

## 四、OBS-1 —— 深层 YAML 蓝图的输入限额（深度/源字节）

**具体问题（证据/复现）**
本轮已把"恶意自引用"关进笼子，但"深而合法的文档仍可能极慢"没有上限可拦。
- 已修（fix 分支，非本裁决项）：YAML 递归锚点解析期 typed 拒绝 + **显式栈守卫**（堆上遍历、内存有界，守卫自身不会栈溢出，`parse.ts` fix 分支 `:173-215` 注释与实现）+ quota 字段安全整数闸（fix 分支 `validate.ts:310` `Number.isSafeInteger`，口径对齐既有 `contracts/src/ids/common.ts` 的 `assertPositiveInteger`，非新造标准）。
- 未裁面（观测值，**不是**任何拟议阈值）：vitest 环境 500 层嵌套 >5s、1000 层约 280s 仍可解（裸 node 约 1k 层即类型化拒绝）；**摄取路径无源字节上限**（rev-A2 实证：`readFileSync` / `bootstrapSource`（`packages/runtime/src/plugin/blueprint-authority.ts:243/:898`、`host.ts:1861`）/ `splitFrontmatter`（`packages/domain/blueprint/src/parse.ts:61`）均无 cap——pre-alpha 既有暴露，非本轮引入）。证据：证据 §4.4、§六 rev-A2 条；`logs/G4-green.txt`、`logs/G4R-green.txt`。

**用户看到什么**
打开一个极深/极大的蓝图（含别名复用）时，界面可能长时间"点了没反应"地卡住，最后要么报类型化错误要么迟迟不出结果。自引用/成环的文档现在会立刻明确报错（已修部分）。

**推荐与备选**
- 方案「加摄取 acceptance 上限」（深度与源字节，具体数值属裁决后的另行分析，本轮不提数）：代价=个别"以前极慢但能成"的深文档改判为秒败（对合法文档是体验收紧）。
- 备选「维持现状」：代价=极慢输入与资源占用面保留；alpha 阶段外部输入面小，风险有限但为 pre-open 面。

**修后影响**
- 用户表现：超限文档从"无响应等待"变"快速、类型化、可行动的错误"。
- 兼容与迁移：仅影响"此前可解但需极端时间"的文档；正常规模蓝图零感知。
- 长期风险：不加=摄取入口的资源上限持续缺位（PM/安全评审每轮都会重新问一遍）；加=数值本身将成为契约的一部分，改数需再裁决。

**❓ 需要您裁决**：是否为蓝图摄取入口裁加"嵌套深度 / 源字节"acceptance 上限（失败要快而明确）——还是接受只有递归守卫 + quota 安全整数闸、不设源体量上限？
