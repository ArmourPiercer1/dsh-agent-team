THE MEASURED CONCLUSION (the reason these numbers are committed rather than quoted)
  * the census wall is 1095606 ms (1095.6 s) = two sequential captures of 550.8 s and 544.8 s, and each
    capture is about its heaviest root window: packages/runtime 545.3 / 543.0 s, packages/testkit
    539.2 / 540.7 s.
  * so ROOT-LEVEL SHARDING CANNOT SHORTEN THIS CENSUS. Whichever shard holds packages/runtime still
    needs 2 x ~543 s = 1086 s; MODEL B predicts 1088254 ms at K=1 against 1095606 ms measured (+0.7%),
    and 1088254 ms at K=2 and K=4 as well: the split buys ~0 s of wall clock.
  * the WORK metric does balance (5226020 ms -> 2614139 ms per shard at K=2), but work is not wall, and
    no work is saved: exactly the same 22 tasks run either way (that is the non-degradation invariant).
  * a sharded run ADDS fixed cost per shard — host provision+build 272 s and repo build 22 s (M0 step
    medians): k=2 adds ~294 s of runner time and one more host boot, k=4 ~882 s and three more, for
    zero wall gain on this data. The M3 host-cache key is the lever that would change that, and it is
    not enabled.
  * to shorten the wall you must either shard INSIDE a root (file-level; not M4) or run the two captures
    concurrently — which spec §1 forbids assuming is lossless, and which is why every capture pair is
    one indivisible group in the plan.
