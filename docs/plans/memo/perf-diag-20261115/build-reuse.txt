4) WHAT THIS MEANS FOR A TRUSTED CACHE.
   SAFE: cache the whole provisioned host tree keyed by host_commit + lock + node/pnpm versions
   + platform + build flags (scripts/host-cache-key.mjs already defines exactly these fields and
   a record/verify manifest, and is NOT wired to CI). Restore it to the SAME absolute path the
   runner uses (/home/runner/work/<repo>/<repo>/tests/deepseek-harness-test-use) and the
   bytes verify. The workflow's existing post-build assertions (git rev-parse HEAD == pin;
   apps/cli/lib/bin.js exists; porcelain-empty drift check) are the right place to add the
   manifest verify.
   UNSAFE / WOULD MAKE IT UNSAFE:
     (a) restoring to a DIFFERENT absolute path and then trusting a manifest recorded at the old
         one — it fails closed (MISS) rather than silently passing, but a cache key that omits the
         path while the manifest includes path-dependent bytes would turn a hit into a refusal;
     (b) caching node_modules or any dependency-resolution artifact without the lock in the key;
     (c) treating 'manifest verifies' as 'the build really ran here' — it does not prove
         provenance, only byte equality with a recorded identity (the M3 memo says so);
     (d) a cache whose key omits the build FLAGS (DSH_CLIENT_COMMIT_HASH, ESBUILD_WORKER_THREADS)
         or the node version: those change output bytes.
   UNSAFE FOR A DIFFERENT REASON: caching the PRODUCT build (packages/*/dist, committed artifacts)
   is already covered by check-artifacts-committed.mjs inside the job; caching it would remove the
   freshness check rather than the build.
