# old-path.tsv — what this fixture is, and what it is not

This file is the reviewed golden fixture for the UTE G1-S1 (FS) prototype:
**sixteen** `(request → effect)` pairs measured on the CURRENT legacy path and
serialized by `tests/ute-g1-fs/lib/scenario.mjs`. Ten cover `write`/`read`/`edit`
on the product route-C seam; six cover `read_image` (UTE-3), the fourth member of
the indivisible FS assembly. (A seventeenth pair, `FS-I0-route-c-gap`, pinned the
pre-repair product-route failure and was deleted when the repair landed — see
the composition section below.)

It is a fixture, not a golden oracle: `run-prototype.mjs` compares the prototype
against it field for field, and `capture-old-path.mjs` re-derives it from the
legacy path (exit 1 on any drift or on a contradiction with the corpus design
claim).

## `read_image` composition (re-baselined after the route-C repair)

Every row, including all six `read_image` rows, runs on the PRODUCT route-C
composition (`mountMemberA5sfRealm` + `attachA5sfNativeToolModules`). That was not
true when this fixture was first reviewed: `packages/runtime/team-services/src/mount.ts`
merged only the router's own services into a routed module's deferred children,
so the tool's deferred `read_image` child could not resolve `ctx.fs` and the call
threw `cannot get property "fs" without inject` before any provider call
(GAP-FS-CONTRACT-1 / PD-5). A seventeenth vector (`FS-I0-route-c-gap`) pinned
that product fact and the six other image vectors ran under the world factory's
`post-gap-1` merge, disclosed here.

The 2026-11-20 repair continues a routed module's OWN declared services into its
deferred children, so the FOURTH member is reachable on the product route. The
six `read_image` rows were re-captured on `route-c` and came out BYTE-IDENTICAL
to their `post-gap-1` rows (same committed bytes, same digests, same block
shape); the 10 read/write/edit rows were re-captured byte-identically to the
reviewed baseline. `FS-I0-route-c-gap` was deleted rather than re-pointed,
because `FS-I1-inlane-image` already is the in-lane allow baseline; the
fail-closed shape it recorded is still pinned by the world-factory
`FSB-IMG-1b` fixture (`withheld-fs-continuation`, NOT the product route).

This makes the fourth member reachable; it does not change any Member's
authority, the FS member set, or the retirement verdict.

The `@result:…` effect entry is synthetic (marked with `@`) because `read_image`
produces an attachment, not a filesystem mutation:
`@result:<mediaType>:<w>x<h>|present|<bytes>|<sha256>|blocks=<shape>`. The digest
is over the bytes the ATTACHMENT STORE received, not over the path string. A
refusal records `@result:none|absent|-|-|-` (no attachment materialised).

## KNOWN-SEMANTIC-DIFFERENCE

The corpus grades effects and refusal CLASSES, so it tolerates known semantic
differences between the two host generations. Those differences are recorded —
with cause and retirement-blocking status — in the sibling file
`SEMANTIC-DIFFERENCES.md`, declared in `../lib/semantic-differences.mjs`, printed
by `run-prototype.mjs` on every run and asserted by `../lane-suite.test.mjs`.
A difference the harness cannot print is not recorded.

## Record shape

Header: `id entry lane_read lane_write outcome refusal codes effects leaks`.

* `lane_*` — world-relative lane tokens, never absolute paths.
* `outcome` — `allow` | `deny`.
* `refusal` — closed class or `-` when the call was allowed. Classes:
  `lane-deny`, `write-requires-read`, `stale-version`, `route-unresolved`,
  `missing-path`, `image-modality-denied`, `cancelled`, and the honest terminal
  `other`. `other` is NOT used by any corpus row (asserted by
  `../lane-suite.test.mjs` and by the capture guard). The old path's *typed*
  codes are empty here: route-C refusals are prose (`authored locator '…' is
  outside every allow subtree of the lane`, `file has not been read — read the
  file, then retry`, `file changed since it was read — re-read the file, then
  retry`, `cannot get property "fs" without inject`, `read target '…' does not
  exist`, `… does not declare image input`, `tool call aborted before dispatch`),
  which `classifyRefusal` maps onto the same class vocabulary the next host's
  typed codes map onto. The four image-specific classes exist so the corpus can
  tell a route gap from a missing file from a modality refusal from a
  cancellation in the machine-readable column, not only in prose.
  `route-unresolved` remains part of the closed vocabulary but no row emits it
  any more (the pre-repair gap row was deleted; the class still exists because
  the world-factory fixture pins that failure shape).
* `effects` — `path|present|<bytes>|<sha256>|<mode>` joined by `;`; `absent`
  carries `-` for the remaining cells.
* `leaks` — secret tokens that appeared in the model-facing result text (`-`:
  none).

## What it does NOT cover (mirrored in ../README.md §7)

* **Read confinement is not proven.** No effect record can prove an
  unauthorized `read()` did not happen; `FS-R1` pins a refusal + the absence of
  the secret token from result text + unchanged bytes, nothing stronger.
* **Delete / move** — the FS tool family exposes no model-facing delete/move
  tool and the legacy governed provider does not override `deleteFile`/
  `moveFile`, so there is no old-path vector to compare against.
* **`read_image` on the NEW path** — the prototype provider has no image
  support yet, so every `FS-I*` row stays `newPathPending: true`; the new-path
  run cannot reproduce these baselines (PR B2). The old path IS the product
  route-C composition for every row.
* **`read_image` beyond those vectors** — no JPEG/WebP/GIF fixture, no
  downscale/`originalDimensions` arm, no byte-cap (`maxImageBytes`) refusal, no
  extension-less sniff arm, no mid-read cancellation (the corpus can only
  pre-abort before dispatch), no attachment-store failure arm. These are
  explicitly NOT claimed by the fixture.
* **Streaming / byte-range** — not exercised.
* **Live boot** — C1 host-free capture, not a booted run.
