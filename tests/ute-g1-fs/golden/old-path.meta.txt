# old-path.tsv — what this fixture is, and what it is not

This file is the reviewed golden fixture for the UTE G1-S1 (FS) prototype:
**seventeen** `(request → effect)` pairs measured on the CURRENT legacy path and
serialized by `tests/ute-g1-fs/lib/scenario.mjs`. Ten cover `write`/`read`/`edit`
on the product route-C seam; seven cover `read_image` (UTE-3 PR B1), the fourth
member of the indivisible FS assembly.

It is a fixture, not a golden oracle: `run-prototype.mjs` compares the prototype
against it field for field, and `capture-old-path.mjs` re-derives it from the
legacy path (exit 1 on any drift or on a contradiction with the corpus design
claim).

## `read_image` composition (disclosed, not implied)

The PRODUCT route-C composition cannot reach `read_image` at all:
`packages/runtime/team-services/src/mount.ts:445` keeps
`ROUTED_SERVICE_NAMES = ['tools','systemPrompt']`, so the tool's deferred child
cannot resolve `ctx.fs` and the call throws `cannot get property "fs" without
inject` before any provider call (GAP-FS-CONTRACT-1 / PD-5). That product fact is
recorded as `FS-I0-route-c-gap`.

The other six image vectors run the SAME legacy host, SAME real
`@deepseek-ai/dsh-tool-fs` module and SAME confined provider under the world
factory's `post-gap-1` composition — the one-line deferred-inject merge the FS
face already uses to pin the attachment contract. This is disclosed so the
fixture cannot be read as "the unpatched product route serves `read_image`"; it
is NOT. Whether a retirement baseline may be taken under that proposed
composition, rather than requiring the product-route fix first, is an owner
decision and is not decided by this fixture.

The `@result:…` effect entry is synthetic (marked with `@`) because `read_image`
produces an attachment, not a filesystem mutation:
`@result:<mediaType>:<w>x<h>|present|<bytes>|<sha256>|blocks=<shape>`. The digest
is over the bytes the ATTACHMENT STORE received, not over the path string. A
refusal records `@result:none|absent|-|-|-` (no attachment materialised).

## KNOWN-SEMANTIC-DIFFERENCE

The corpus grades effects and refusal CLASSES, so it tolerates known semantic
differences between the two host generations. Those differences are recorded —
with cause and retirement-blocking status — in the sibling file
`SEMANTIC-DIFFERENCES.md`, declared in `../lib/semantic-differences.mjs`, printed
by `run-prototype.mjs` on every run and asserted by `../lane-suite.test.mjs`.
A difference the harness cannot print is not recorded.

## Record shape

Header: `id entry lane_read lane_write outcome refusal codes effects leaks`.

* `lane_*` — world-relative lane tokens, never absolute paths.
* `outcome` — `allow` | `deny`.
* `refusal` — closed class (`lane-deny`, `write-requires-read`, `stale-version`,
  `other`) or `-` when the call was allowed. The old path's *typed* codes are
  empty here: route-C refusals are prose (`authored locator '…' is outside every
  allow subtree of the lane`, `file has not been read — read the file, then
  retry`, `file changed since it was read — re-read the file, then retry`), which
  `classifyRefusal` maps onto the same class vocabulary the next host's typed
  codes map onto.
* `effects` — `path|present|<bytes>|<sha256>|<mode>` joined by `;`; `absent`
  carries `-` for the remaining cells.
* `leaks` — secret tokens that appeared in the model-facing result text (`-`:
  none).

## What it does NOT cover (mirrored in ../README.md §7)

* **Read confinement is not proven.** No effect record can prove an
  unauthorized `read()` did not happen; `FS-R1` pins a refusal + the absence of
  the secret token from result text + unchanged bytes, nothing stronger.
* **Delete / move** — the FS tool family exposes no model-facing delete/move
  tool and the legacy governed provider does not override `deleteFile`/
  `moveFile`, so there is no old-path vector to compare against.
* **`read_image` on the PRODUCT route-C composition** — it is dead there
  (PD-5), so only its failure is pinned (`FS-I0-route-c-gap`). The allow/lane/
  route/cancel image vectors run under the disclosed `post-gap-1` composition.
* **`read_image` beyond those vectors** — no JPEG/WebP/GIF fixture, no
  downscale/`originalDimensions` arm, no byte-cap (`maxImageBytes`) refusal, no
  extension-less sniff arm, no mid-read cancellation (the corpus can only
  pre-abort before dispatch), no attachment-store failure arm. These are
  explicitly NOT claimed by the fixture.
* **Streaming / byte-range** — not exercised.
* **Live boot** — C1 host-free capture, not a booted run.
